# 智能问数接口 · 对接说明（v2.4）

> **v2.0 相比 v1.0 新增：多轮上下文（会记住上一轮）、历史对话列表、历史对话记录、回答评价。**
> v1.0 的调用方式**完全兼容** —— 老代码不改也能跑（只是用不上这些新能力）。
>
> **v2.4（2026-09-22）错误码规范化 + 全接口体检**：
> ① 传错参数**一律返 400**（之前有几处会返 500 甚至直接掐断连接）；
> ② 新增**全局异常兜底** —— 任何未预料的异常都回一个 500 JSON 并记日志（以前客户端只会看到"空响应"）；
> ③ 请求体不是合法 JSON 时，`/api/ask` 与 `/api/feedback` 返 **400 并说明是 JSON 错**
>    （以前会被当成"没传 body"，返回 200 + `问题为空`，很误导）。
> 详见第七节新增的「错误码约定」。**对正确调用的客户端零影响。**
>
> **v2.3（2026-09-22）给 L2 摘要加了两道注入闸 + 新增 `summary_skip` 字段**：
> ① `history_turns=0` 现在**会连摘要一起关掉**（之前摘要会绕过它溜进来，是个 bug）；
> ② 会话总轮数 < `SECRETARY_SUMMARY_MIN_TURNS`（默认 6）时不注入（短会话 history 已覆盖全场）。
> 响应新增 `summary_skip`，直接写明"本轮为什么没用摘要"，排查记忆问题先看它。
> **对调用方仍是兼容变更**（只是以前"不该注入时会注入"的情况被修掉了）。
>
> **v2.2（2026-09-22）新增「L2 会话摘要」**：长会话的早期轮次会被压缩成摘要，
> 续聊时自动注入，于是"翻出以前的历史对话继续聊"能记住更早的内容。
> 响应里多 `summary_used` / `summary_chars` / `summary_upto_seq` / `history_injected`。
> **前端不用改任何东西**（`session_id` 照旧传）。见第三节「多轮对话怎么用」。
>
> **v2.1（2026-09-22）改了两个历史接口的默认行为**，调用方要注意：
>
> | 接口 | 改动 |
> |---|---|
> | `GET /api/sessions` | **默认返回全部会话**（原来是 20 条、最多 200）；`total` 修正为真实总数，新增 `returned` / `truncated` |
> | `GET /api/history` | **默认返回该会话全部消息**（原来是 200 条、最多 1000）；新增 `returned` / `truncated` |
>
> 想要旧的分页行为，显式传 `limit=20` 即可 —— **参数语义完全兼容**，只是不传时的默认值变了。

## 三、提问：POST /api/ask

```
POST /api/ask
Content-Type: application/json
```

**请求体**

```json
{
  "question": "环潭供电所上个月的线损率",
  "session_id": "s_5f224f10aaed42a2bbcf45e2d0c504dd",
  "uid": "PROV-FIN-001",
  "model": "qwen3.8-max",
  "profile": "关注线损与停电时长"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `question` | ✅ | 用户的原话。**不用预处理**——错字、简称、没写时间地点都能直接问 |
| `session_id` | | **会话ID**。多轮对话 / 需要历史记录时传；**不传服务端会生成一个并在响应里返回** |
| `uid` | | 业务用户ID（如 `PROV-FIN-001`）。用于把会话归到人名下。不传则该会话没有归属人 |
| `history_turns` | | 本轮带几轮上下文，默认 5（`SECRETARY_HISTORY_TURNS`）；**传 `0` = 本次不带上下文** |
| `user_name` | | 用户名称（可选，仅回显，不入库为主字段） |
| `channel` | | 来源渠道，如 `web` / `app` / `wecom`；不传按 `webapi` 记 |
| `model` | | 指定模型，不传用默认 `qwen3.8-max` |
| `max_steps` | | 工具调用步数上限，不传=不限 |
| `profile` | | 用户画像文本（可选，用于判断关注重点） |

> **`user_id`（数字）也可以传**，但推荐用 `uid` —— 那是业务用户ID，服务内部会换成主键。

**响应体**（`answer` 是你唯一必须关心的字段）

```json
{
  "answer": "环潭供电所2026年8月线损率数据缺失，最近可用数据为截至2026年9月的本年累计台区线损率为3.65%。",
  "session_id": "s_5f224f10aaed42a2bbcf45e2d0c504dd",
  "qa_id": 1,
  "input_question": "环潭供电所上个月的线损率",
  "fixed_question": "环潭供电所2026年8月的线损率",
  "completed_question": "环潭供电所2026年8月的线损率",
  "completion_used": false,
  "name_fix_used": false,
  "scope": {
    "time": "2026年8月",
    "period_type": "month",
    "period_key": "202608",
    "time_is_default": false,
    "place": "环潭供电所",
    "place_is_default": false,
    "time_inherited": false,
    "place_inherited": false
  },
  "history_used": 2,
  "history_injected": 2,
  "summary_used": false,
  "summary_chars": 0,
  "summary_upto_seq": 0,
  "summary_skip": "会话共 5 轮 < SUMMARY_MIN_TURNS=6",
  "model": "qwen3.8-max",
  "elapsed_ms": 12573,
  "timings": {"namefix_ms": 0, "completion_ms": 1373, "loop_ms": 10700, "total_ms": 12573},
  "db_query_count": 2,
  "sql_query_count": 2,
  "kb_query_count": 0,
  "no_db_query": false,
  "unverified": false,
  "steps": 6
}
```

| 返回字段 | 说明 |
|---|---|
| **`answer`** | **回答正文，直接展示给用户** |
| **`session_id`** | **会话ID。存下来，下次提问带回来就是同一场会话** |
| **`qa_id`** | **本次回答的记录ID。做「点赞/点踩」时用它** |
| `input_question` | 你传进来的原话（回显） |
| `fixed_question` | 纠错 + 补全时间地点后的问题（可显示在"我理解为…"） |
| `completed_question` | 再过一遍问题补全规则后的最终查询问题 |
| `completion_used` | 补全规则是否产出了不同内容 |
| `name_fix_used` | 是否发生了错字纠正 / 名称归一 |
| `scope` | 识别出的统计口径（时间/地点），便于前端提示口径。其中 `time_inherited` / `place_inherited` 为 `true` 表示该值**是从上一轮沿用的**，不是本轮说的 |
| `history_used` | 本轮读到了几轮上下文（上限 5，含已被摘要覆盖的轮次）|
| **`history_injected`** | 其中**真正塞进提示**的有几轮。因为已摘要覆盖的轮次不重复塞，所以它常小于 `history_used`；最近 2 轮始终会带（保证追问精细度）|
| **`summary_used`** | 本轮是否用了**会话摘要**（L2 记忆）。`true` 表示这场会话的早期轮次被压缩成一段话注入了 —— 这就是"翻出旧会话继续聊还能记住前文"的来源 |
| **`summary_chars`** | 摘要字数（0 = 没用摘要）|
| **`summary_upto_seq`** | 摘要覆盖到第几条消息；`history_injected` 只管这之后的部分 |
| **`summary_skip`** | **本轮为什么没用摘要**（`null` = 正常用了或不适用）。取值如 `history_turns=0（本轮不要记忆）`、`会话共 5 轮 < SUMMARY_MIN_TURNS=6`。排障时先看它 |
| `model` | 实际使用的模型 |
| `elapsed_ms` / `timings` | 总耗时 / 分阶段耗时（纠错、补全、主循环） |
| `db_query_count` / `sql_query_count` / `kb_query_count` | 查库次数 / SQL 条数 / 知识库检索次数 |
| `no_db_query` | `true` = 一次库都没查（凭已有知识作答，需警惕） |
| **`unverified`** | **`true` = 没查库就下结论、已被拦下，这条回答不可信** |
| `steps` | 工具调用步数 |
| `trace` | 全过程明细（每步工具调用、SQL、耗时），调试用，正常展示不用管 |

> `no_db_query` 和 `unverified` 不一样：前者只是"没查库"这个事实，后者是"没查库还想给结论、结果被拦下"。
> **要当故障看的是 `unverified = true`。**
>
> `qa_id` 为 `null` 说明这次没落库（记录库不可用），问答本身不受影响，但这次无法评价、也进不了历史。

### 多轮对话怎么用

服务端**不保存上下文**，多轮由你这边把 `session_id` 带回来即可：

```python
# 第 1 轮：不传 session_id
r1 = ask("环潭供电所上个月的线损率")
sid = r1["session_id"]          # 存起来

# 第 2 轮：带回同一个 session_id
r2 = ask("那全市的呢", session_id=sid)

# 用 session_id 查历史
GET /api/history?session_id={sid}
```

**注意**：`session_id` **不只是归档用的** —— 服务端会把该会话**最近 5 轮**问答作为上下文，
所以省略主语的追问能听懂：

**★ 也可以"翻出以前的历史对话继续聊"**：先用 `GET /api/sessions` 列出历史，
拿到某场会话的 `session_id` 后，**在 `POST /api/ask` 里回传同一个 `session_id`** 就是接着那场聊。
响应里的 `history_used` 告诉你这次实际带上了几轮历史 —— 它是 `0` 就说明记忆没生效（多半是 session_id 传错或那场会话没落库）。

### ★ 长会话靠"会话摘要"记住前文（L2 记忆，2026-09-22 新增）

只带最近 5 轮有个硬伤：**一场聊了很久的会话，早期内容会被挤出上下文**。
所以服务端会自动给每场会话生成 **摘要**，续聊时一起注入：

| 机制 | 什么时候发生 | 你能看到什么 |
|---|---|---|
| 摘要生成 | 后台**异步**，每攒够 5 轮问答做一次（不占问答耗时）| 无感；只影响记忆效果 |
| 摘要注入 | 每次提问，**但要过两道闸**（见下）| 响应里 `summary_used=true`、`summary_chars=113` |
| 明细去重 | 摘要已覆盖的轮次不再重复注入；**最近 2 轮永远原样带**（且不会被写进摘要）| `history_injected` 会小于 `history_used` |

**★ 两道注入闸（2026-09-22 加，都是踩过的坑）：**

| 闸 | 条件 | 为什么 | 没注入时 `summary_skip` 长什么样 |
|---|---|---|---|
| ① | `history_turns=0` | 调用方写 0 就是"本轮**完全**不要记忆"，摘要不能绕过这个开关溜进来 | `history_turns=0（本轮不要记忆）` |
| ② | 会话总轮数 < `SECRETARY_SUMMARY_MIN_TURNS`（默认 **6**）| 短会话的 history 已经把全场带上了，再注入摘要是**纯重复** | `会话共 5 轮 < SUMMARY_MIN_TURNS=6` |

> 这两道闸只影响**注入**，不影响**生成** —— 摘要照旧在后台生成，会话聊长后自然就会注入。
> 排查"记忆怎么没生效"时，**先看 `summary_skip`**，它直接告诉你原因。

**对前端的影响：几乎没有** —— 不需要传任何新参数，`session_id` 照旧传就行。
唯一建议：如果你想在界面上标注"已记住前文"，可以看 `summary_used`。

> ⚠️ **摘要里不写业务数字**（金额、百分比、件数等），只写"关注对象 / 已确认口径 / 结论"。
> 所以就算摘要有偏差，也不会污染本轮的数据 —— 每次回答的数字仍然来自本轮实时查库。
> 想关掉这个能力：服务端设 `SECRETARY_SESSION_SUMMARY=0`（问答不受影响，只是不再跨轮记忆）。

| 第几轮 | 你问 | 系统理解成 |
|---|---|---|
| 1 | 环潭供电所上个月的线损率 | 环潭供电所 · 2026年8月 |
| 2 | **那售电量呢** | 环潭供电所 · 2026年8月（时间地点都沿用上一轮） |
| 3 | **那全市的呢** | 全市 · 2026年8月（地点改全市，时间仍沿用） |
| 4 | **今年的呢** | 全市 · 2026年1-9月（时间改累计，地点沿用全市） |

**规则**（很重要，决定你怎么用）：

1. **本轮说了就用本轮的**，只有本轮**完全没提**时才沿用上一轮。
2. 沿用是**推断**，不是事实 —— 响应里 `scope.time_inherited` / `scope.place_inherited`
   会告诉你哪些值是沿用的，前端可以据此提示用户「按上一轮的口径理解」。
3. 上下文长度默认 **最近 5 轮**，可用请求参数 `history_turns` 调整；传 `0` = 本次不带上下文。
4. **不传 `session_id` 就没有上下文**（每次提问独立），适合一次性查询。
5. 沿用来的时间**不会改写你的问题原文**，只在【统计范围】里说明。

> 想让它完全回到"每次独立"的行为：请求里传 `"history_turns": 0`，
> 或服务端设 `SECRETARY_HISTORY_TURNS=0` 全局关掉。

## 四、历史对话列表：GET /api/sessions

看某个人/所有人说过哪些话。一行 = 一场会话，按最后活动时间倒序。

```
GET /api/sessions?uid=PROV-FIN-001&limit=20&offset=0
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `uid` | | 只看某个用户的会话；不传 = 全部 |
| `limit` | | **不传（或传 0）= 一次返回全部**；传正整数 = 分页取前 N 条 |
| `offset` | | 跳过多少条（翻页），默认 0 |

> ★ **默认就是"全部返回"**（2026-09-22 起）。老版本默认只给 20 条、且最多 200 条，现在没有这个硬上限了。
>
> 唯一的刹车是**防呆上限**：一次最多 `5000` 条（服务端 `SECRETARY_API_MAX_ROWS` 可调），
> 真被截断时响应里 `truncated` 会是 `true` —— **前端看到它就该改用 `limit`+`offset` 分页往下取**，
> 而不是以为"总共就这么多"。要一次拿全量只要不传 `limit`（库里现在几百场，远没到上限）。

**响应**

```json
{
  "total": 170,
  "returned": 170,
  "limit": 5000,
  "offset": 0,
  "truncated": false,
  "sessions": [
    {
      "session_id": "s_5f224f10aaed42a2bbcf45e2d0c504dd",
      "user_code": "PROV-FIN-001",
      "title": "环潭供电所上个月的线损率",
      "ai_model": "qwen3.8-max",
      "channel": "webapi",
      "client_ip": "127.0.0.1",
      "msg_count": 4,
      "status": 1,
      "create_time": "2026-09-20 15:37:41",
      "last_msg_at": "2026-09-20 15:37:51",
      "ended_at": null,
      "ask_count": 2,
      "gap_count": 0
    }
  ]
}
```

**外层字段（分页控制，★ 前端判断有没有被截断就看这几个）**

| 字段 | 说明 |
|---|---|
| **`total`** | **符合条件的会话总数**（不受 limit/offset 影响）—— 这个才是"总共多少场" |
| `returned` | 本次实际返回条数（= `sessions` 数组的长度）|
| `limit` | 本次生效的条数上限（"全部返回"时等于防呆上限 5000）|
| `offset` | 本次的偏移 |
| `truncated` | `true` = 因超过防呆上限被截断，请用 `limit`+`offset` 继续取下一页 |

> ⚠️ **老版本这里有个坑**：`total` 填的是"本页条数"，前端看到 `total=20` 会以为库里总共只有 20 场。
> 2026-09-22 已修正 —— 现在 `total` 是真实总数、`returned` 才是本页条数。

**`sessions[]` 里每行的字段**

| 字段 | 说明 |
|---|---|
| `session_id` | 会话ID，拿去查历史详情 |
| `title` | 会话标题，**取该会话的第一句提问** |
| `user_code` | 提问人（业务用户ID），没传 `uid` 时为 `null` |
| `msg_count` | 消息条数（一问一答算 2 条） |
| `ask_count` | **提问次数**（= 问答轮数，比 `msg_count` 直观） |
| `gap_count` | 其中答不上来的次数（查不到 / 无此口径） |
| `status` | 1进行中 / 2已结束 / 3已归档 |
| `create_time` / `last_msg_at` / `ended_at` | 创建 / 最后消息 / 结束时间（`ended_at` 未结束时为 `null`）|
| `ai_model` | 这场会话用的模型 |
| `channel` | 来源渠道（如 `webapi`）|
| `client_ip` | 调用方 IP |

## 五、历史对话记录：GET /api/history

看某场会话里**每一句问答**，以及每次回答的口径与质量。

```
GET /api/history?session_id=s_5f224f10aaed42a2bbcf45e2d0c504dd&limit=200&with_steps=0
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `session_id` | ✅ | 会话ID（不存在返回 **404**） |
| `limit` | | **不传（或传 0）= 返回该会话全部消息**；传正整数 = 只取最早的 N 条（按 `seq_no` 正序）|
| `with_steps` | | 传 `1` 时，每条 AI 回答会带上**执行步骤明细**（调了什么工具、SQL、耗时） |

> ★ 和列表接口一样，默认**全部返回**，只受防呆上限（默认 5000）保护；被截断时 `truncated=true`。
> 实测一场会话最多几十条消息，正常不会触碰上限。

**响应**

```json
{
  "session": {
    "session_id": "s_5f224f10aaed42a2bbcf45e2d0c504dd",
```

**外层字段**

| 字段 | 说明 |
|---|---|
| `session` | 这场会话的概要 —— 含 `session_id` / `user_code` / `title` / `ai_model` / `channel` / `msg_count` / `status` / `create_time` / `last_msg_at` / `ended_at`（字段含义同第四节的 `sessions[]` 每行，但**不含** `ask_count` / `gap_count` / `client_ip`）|
| **`total`** | **该会话的消息总数**（不受 `limit` 影响）|
| `returned` | 本次实际返回条数（= `messages` 数组长度）|
| `limit` | 本次生效的上限；"全部返回"时等于防呆上限 5000 |
| `truncated` | `true` = 被防呆上限截断 |
| `messages` | 消息数组，**按 `seq_no` 正序**（询问在前、回答在后）|

**每条消息怎么看：**

| 字段 | 说明 |
|---|---|
| `id` | 消息主键（本表唯一，**跨会话可能重复用于排序无关**；展示顺序请用 `seq_no`）|
| `seq_no` | 会话内顺序号，**按它排序展示**（从 1 开始） |
| `sender_type` | **1 = 用户，2 = AI**，3 = 系统，4 = 人工坐席 |
| `sender_id` | 发送者内部ID（用户侧对应 `t_user.id`，AI 侧为 `null`）|
| `direction` | 1 入站 / 2 出站。**以 `sender_type` 为准**，这个只用于左右分组 |
| `msg_type` | 消息类型，`1` = 文本（当前只有这一种）|
| `content` | 消息正文 |
| `reply_to_id` | **AI 回答指向它回复的那条用户消息**（做「重新生成」时用） |
| `qa_id` | **只有 AI 回答才有**，用来评价；用户消息是 `null` |
| `model` | 生成这条回答用的模型（用户消息为 `null`）|
| `latency_ms` / `elapsed_ms` | 这条 AI 回答耗时（`latency_ms` 落库值，`elapsed_ms` 同源；用户消息为 `null`）|
| `create_time` | 消息时间 |

**AI 回答独有（做"我理解为…"、口径提示、可信度标记）：**

| 字段 | 说明 |
|---|---|
| `fixed_question` | 纠错+补全后的理解，可展示成「我理解为：…」 |
| `completed_question` | 补全节点**最终认为**的问题（通常同 `fixed_question`；没套上规则时就是原样）|
| `name_fix_used` / `completion_used` | 是否做了纠错 / 是否套了补全规则 |
| `period_type` / `period_key` / `time_text` | 时间口径（`month`/`year`/`yearToDate`、`202608`、`2026年8月`） |
| `place` / `place_is_default` | 地点；`place_is_default=1` 说明用户没写地点，按**全市**处理 |
| `time_is_default` | `1` = 用户没写时间，按**今年至今**处理 |
| `db_query_count` / `sql_query_count` / `kb_query_count` | 本轮查库次数 / 其中 SQL 次数 / 知识库检索次数 |
| `no_db_query` | `1` = 这轮**一次库都没查**（通常意味着是闲聊或业务外问题）|
| `unverified` | **`1` = 这条回答不可信**（模型没查库就下结论，已被拦下） |
| `is_gap` | `1` = 答不上（查不到 / 无此口径） |
| `feedback` | `1` 赞 / `0` 踩 / `null` 未评价 |
| `feedback_note` | 评价时的备注（`null` = 没写）|

**`with_steps=1` 时**多一个 `steps` 数组（每次回答的每一步）：

```json
"steps": [
  {"step_no": 1, "step_kind": "scope",    "tool_name": "time_scope",  "cost_ms": 470},
  {"step_no": 3, "step_kind": "tool",     "tool_name": "run_sql",     "result_rows": 0, "cost_ms": 98},
  {"step_no": 6, "step_kind": "answer",   "cost_ms": null}
]
```

`step_kind` 取值：`namefix` 纠错 / `scope` 时间地点补全 / `complete` 问题补全 / `tool` 调工具 / `nudge` 被要求先核实 / `answer` 给出答案 / `blocked` 被拦下。

> 这个字段是给**排查问题**用的（"为什么这次查了 5 次才查到"），前端默认不用展示。

## 六、评价：POST /api/feedback

```
POST /api/feedback
Content-Type: application/json

{"qa_id": 1, "feedback": 1, "note": "答得准"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `qa_id` | ✅ | 取 `/api/ask` 响应里的 `qa_id`，**必须是从响应里原样拿的整数**（不能传字符串 `"nope"` 这类）|
| `feedback` | ✅ | `1` 赞，`0` 踩（必须是数字或数字字符串）|
| `note` | | 备注（踩的时候写原因最有用） |

**响应**：`{"ok": true, "updated": 1, "qa_id": 1, "feedback": 1}`

`updated: 0` 说明 `qa_id` 不存在（**这不是错误**，200 返回）。

**会返 400 的三种情况**（都是调用方传错，不是服务故障）：

| 情况 | 返回 |
|---|---|
| 没传 `qa_id` | `{"error": "缺少 qa_id（取 /api/ask 返回里的 qa_id）"}` |
| `qa_id` 不是整数（如 `"nope"`）| `{"error": "qa_id 必须是整数（取 /api/ask 返回里的 qa_id）"}` |
| `feedback` 不是 0/1 | `{"error": "feedback 必须是 1（赞）或 0（踩）"}` |
| 请求体不是合法 JSON | `{"error": "请求体不是合法 JSON：JSONDecodeError: …"}` |

## 七、注意事项

1. **超时设 90 秒**。单次问答要查库 + 调大模型，5~30 秒是常态。
2. **别高并发**。服务是单进程多线程，批量请**串行调用**，或提前跟我们对一下节奏。
3. **接口没有鉴权，地址是公网 IP** —— 知道地址的人都能查到全部业务数据，
   包括**历史对话记录**。请勿把地址转发到外部、不要写进对外文档或截图。
4. **有登录态就把 `uid` 传上**。不传的话所有会话都没有归属人，按人统计/按人查历史都做不了；
   而且**这些数据以后补不了**（当前用户身份只能由调用方提供，服务端不校验）。
5. 需要**新指标 / 新口径**，或发现答案不对，找我们反馈时**附上 `session_id` 和 `qa_id`** ——
   有这两个我们能直接定位到当时的每一步。

### 错误码约定（2026-09-22 起）

| 码 | 含义 | 你要做什么 |
|---|---|---|
| **200** | 成功。**注意**：业务上的"查不到 / 不存在"也走 200（如 `updated:0`、`total:0`）| 正常解析 body |
| **400** | **调用方传错**：缺必填参数、类型不对、请求体不是合法 JSON | 修请求；错误原因在 `error` 字段里 |
| **404** | 资源不存在（`/api/history` 的 `session_id` 查不到、知识库文件没有本地副本）| 见 `error` 说明 |
| **500** | **服务端故障**。2026-09-22 起所有未预料的异常都会兜成这个（以前会直接掐断连接，客户端只看到"空响应"）| 把 `error` 全文给我们 |

> **★ 两类错误的区分很重要**：400 是"你传错了"（改请求就行），500 是"我们的问题"（要找我们）。
> 之前有几处传错参数会返 500，已修 —— 现在**传错参数一律 400**，不会再让排查方向跑偏。

## 八、怎么问效果最好

**直接用大白话问就行**，不用自己拼时间地点。下面这些都能正确理解：

| 你问 | 系统会理解成 |
|---|---|
| 环潭供电所的线损率 | 环潭供电所 · 今年 1-9 月累计 |
| 环潭供电所**上个月**的线损率 | 环潭供电所 · **2026年8月** |
| **本月**的售电量 | 全市 · **2026年9月** |
| **环谈**供电所的售电量 | 自动纠正为**环潭**供电所（错字/同音字） |
| **凉水**供电所的售电量 | 自动归一为**两水**供电所（简称） |
| **公家棚**的线损率 | 自动归一为**龚家棚**台区（地名层） |

没写地点 → 默认**全市**；没写时间 → 默认**今年 1 月至今（累计口径）**。
这两点在响应里能用 `place_is_default` / `time_is_default` 判断出来。

### 已知边界（避免误判成故障）

1. **"某供电所上个月"这类问法通常查不到值**。数据表里供电所粒度**只有年度和本年累计，
   没有当月口径**，且月度数据本身有缺失。系统会明确回答「X月数据缺失，最近可用的是…」，
   这是正常的，不是报错。
2. **当年数据用"本年累计"口径**（如 2026 年 1-9 月），不是"全年"。
3. 库里没有的指标（酒店入住率、GDP 等）会**如实拒答**，这是设计要求。

## 九、调用示例

### curl

```bash
curl -X POST http://47.121.183.81:8200/api/ask \
  -H "Content-Type: application/json" \
  -d '{"question":"环潭供电所上个月的线损率","uid":"PROV-FIN-001"}' \
  --max-time 90
```

### Python（完整流程：提问 → 查历史 → 评价）

```python
import requests

B = "http://47.121.183.81:8200"
S = requests.Session()

# 1) 提问（第 1 轮不传 session_id）
r = S.post(B + "/api/ask", json={"question": "环潭供电所上个月的线损率",
                                 "uid": "PROV-FIN-001"}, timeout=90).json()
print(r["answer"])
sid, qa_id = r["session_id"], r["qa_id"]

# 2) 追问（把 session_id 带回去）
r2 = S.post(B + "/api/ask", json={"question": "那全市的呢",
                                  "session_id": sid, "uid": "PROV-FIN-001"}, timeout=90).json()
print(r2["answer"])

# 3) 历史对话列表
for s in S.get(B + "/api/sessions", params={"uid": "PROV-FIN-001", "limit": 10}, timeout=30).json()["sessions"]:
    print(s["last_msg_at"], s["title"], "共%d问" % s["ask_count"])

# 4) 某场会话的明细
h = S.get(B + "/api/history", params={"session_id": sid}, timeout=30).json()
for m in h["messages"]:
    who = "用户" if m["sender_type"] == 1 else "AI"
    print("[%s] %s: %s" % (m["create_time"], who, m["content"][:40]))

# 5) 评价
S.post(B + "/api/feedback", json={"qa_id": qa_id, "feedback": 1, "note": "答得准"}, timeout=30)
```

### Java

```java
import java.net.URI;
import java.net.http.*;
import java.nio.charset.StandardCharsets;
import java.time.Duration;

var client = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(10)).build();

String body = "{\"question\":\"环潭供电所上个月的线损率\",\"uid\":\"PROV-FIN-001\"}";
var req = HttpRequest.newBuilder()
        .uri(URI.create("http://47.121.183.81:8200/api/ask"))
        .timeout(Duration.ofSeconds(90))            // 关键：给够时间
        .header("Content-Type", "application/json")
        .POST(HttpRequest.BodyPublishers.ofString(body, StandardCharsets.UTF_8))
        .build();

var resp = client.send(req, HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8));
System.out.println(resp.body());                     // JSON，取 answer / session_id / qa_id

// 历史列表
var listReq = HttpRequest.newBuilder()
        .uri(URI.create("http://47.121.183.81:8200/api/sessions?uid=PROV-FIN-001&limit=10"))
        .timeout(Duration.ofSeconds(30)).GET().build();
System.out.println(client.send(listReq, HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8)).body());
```

## 十、健康检查

```
GET /health
→ {"ok": true, "model": "qwen3.8-max", "name_fix": true, "qa_log": true}
```

| 字段 | 含义 |
|---|---|
| `ok` | 服务活着 |
| `model` | 当前默认模型 |
| `name_fix` | **纠错/归一是否生效**（`false` 时错字不会被纠正，问答仍可用） |
| `qa_log` | **对话记录是否落库**（`false` 时历史接口查不到新数据，问答仍可用） |

后两个为 `false` 时会附一个 `*_reason` 说明原因。**探活判 `ok` 就够**；
`name_fix` / `qa_log` 为 `false` 不需要你们报警，但**请告知我们**。
