## 二、本次新增的表（4.1~4.5）

### 2.1 这三张表解决什么问题

在这批改动之前，知识库的文件**只存在于阿里云百炼云端**，我们本地一无所知。带来的问题是：

- 想看文件内容 → **百炼没有"下载原文"和"按页取文本"这两个能力**，做不了预览
- 上传只能同步等（最长 300 秒）→ 没法异步
- 谁传的、什么时候传的、抽没抽过 → 没有台账，无从查

于是加了本地台账层：**原文落磁盘，元信息与正文入库**。

```
磁盘：{KB_FILE_ROOT}/{index_id}/{md5}/{原文件名}     ← 原文件二进制（不在库里）
MySQL：t_kb_file（台账）+ t_kb_file_page（按页 HTML）← 元信息与正文
```

> ★ **为什么原文不入库**：几十上百 MB 的二进制塞 BLOB 会把备份、查询、迁移全拖慢。
> 只把"文件的信息"和"文件的内容（文本）"放进库里。

### 2.2 `t_kb_file` —— 文件台账

**干什么**：每一行对应知识库里的一份文档，记录它是谁、多大、存在哪、抽没抽完。
**它是整个预览/下载/审计功能的地基** —— 列表接口、预览接口、删除都靠它。

```sql
CREATE TABLE `t_kb_file` (
  `id`            bigint       NOT NULL AUTO_INCREMENT        COMMENT '主键',
  `file_id`       varchar(64)  NOT NULL                       COMMENT '云端文件ID（百炼 fileId），对账主键',
  `index_id`      varchar(32)  NOT NULL                       COMMENT '所属知识库ID',
  `file_name`     varchar(255) NOT NULL                       COMMENT '原始文件名（含后缀）',
  `file_ext`      varchar(16)  DEFAULT NULL                   COMMENT '小写后缀，如 pdf / docx',
  `size_bytes`    bigint       DEFAULT NULL                   COMMENT '字节数',
  `md5`           char(32)     DEFAULT NULL                   COMMENT '内容MD5，用于秒传/去重',
  `storage_path`  varchar(500) DEFAULT NULL                   COMMENT '原文件磁盘路径；控制台直接传的为 NULL',
  `origin`        varchar(16)  NOT NULL DEFAULT 'api'         COMMENT '来源：api=本服务上传 / console=百炼控制台传的',
  `page_count`    int          NOT NULL DEFAULT '0'           COMMENT '抽取出的页数（0=还没抽）',
  `text_chars`    int          NOT NULL DEFAULT '0'           COMMENT '抽出的正文总字符数',
  `text_format`   varchar(16)  NOT NULL DEFAULT 'html'        COMMENT '文本格式：html（富文本，前端直接渲染）',
  `extract_status` varchar(16) NOT NULL DEFAULT 'pending'     COMMENT 'pending/extracting/done/failed/unsupported',
  `extract_error` varchar(500) DEFAULT NULL                   COMMENT '抽取失败原因（给人看的）',
  `extract_ms`    int          DEFAULT NULL                   COMMENT '抽取耗时（毫秒）',
  `uploader`      varchar(64)  DEFAULT NULL                   COMMENT '上传人（业务用户ID）',
  `upload_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `deleted_flag`  tinyint      NOT NULL DEFAULT '0'           COMMENT '删除标记：0正常 1删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_index_file` (`index_id`,`file_id`),
  KEY `idx_md5` (`md5`),
  KEY `idx_status` (`extract_status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='知识库文件台账';
```

**★ 两个字段要特别理解：**

| 字段 | 为什么重要 |
|---|---|
| **`origin`** | `api` = 本服务上传的（**本地有副本，能预览能下载**）；<br>`console` = 在百炼控制台直接传的（**本地没有副本，预览和下载都会 404**）。<br>文档列表接口里"控制台传的文件无法显示预览"就是看这个字段 |
| **`extract_status`** | 抽取状态机，见下 |

**`extract_status` 状态机：**

```
pending ──→ extracting ──→ done        ✅ 抽好了，可预览
                      └──→ failed      ❌ 抽失败，看 extract_error
                      └──→ unsupported ⚠ 这种格式不支持（老式 .doc、图片等），下载仍可用

（另有 none = 控制台传的、本地无副本，只出现在接口响应里，不落库）
```

**重要约定：**

- ★ **上传顺序是"先落盘 → 再传云端 → 成功后才记台账"**。云端失败就把刚落盘的文件删掉，不留孤儿文件
- ★ `skip_if_exists=1`（同名已存在）时**不覆盖已有台账** —— 同名文件的字节不保证一致，
  覆盖会让 `file_id` 指向错的内容
- **删除文档默认只软删台账（`deleted_flag=1`），磁盘原文保留**；要连原文一起删需传 `drop_raw=1`

### 2.3 `t_kb_file_page` —— 按页富文本

**干什么**：一份文件抽出来的正文，**一行一页**。前端预览时逐页取。

```sql
CREATE TABLE `t_kb_file_page` (
  `id`         bigint      NOT NULL AUTO_INCREMENT COMMENT '主键',
  `file_id`    varchar(64) NOT NULL                COMMENT '关联 t_kb_file.file_id',
  `page_no`    int         NOT NULL                COMMENT '页码，从 1 开始',
  `page_label` varchar(64) DEFAULT NULL            COMMENT '展示用标签：第 3 页 / Sheet1 / Slide 2 / 第 2 节',
  `content`    mediumtext                          COMMENT '正文，HTML 富文本（已做 XSS 白名单清洗）',
  `char_count` int         NOT NULL DEFAULT '0'    COMMENT '本页字符数（按纯文本计）',
  `create_time` datetime   NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_file_page` (`file_id`,`page_no`),
  KEY `idx_file` (`file_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='知识库文件按页富文本';
```

**★ 为什么按页存，而不是整篇塞进 `t_kb_file` 的一个字段：**

1. **前端可以逐页加载**：大文件（几十 MB 的 PDF）不会一次撑爆
2. **将来要全文检索**可以直接在这张表上建 FULLTEXT 索引
3. **重抽只影响这张表**，台账不动

**"天然分页"规则**（前端看到的 `page_label` 由此而来）：

| 文件类型 | 一页是什么 |
|---|---|
| PDF | **每一 PDF 页** |
| XLSX | **每个 sheet** |
| PPTX | **每张 slide** |
| DOCX / MD / TXT | 按字数切块（约 2000 字一块）|

> ⚠️ **已知局限**：跨页的表格会被切断（表头在第 2 页、数据在第 3 页时，第 3 页只剩数据行）。
> 前端按页顺序连续阅读不受影响。

**★ 安全**：`content` 里的 HTML **在入库前已经过白名单清洗**（`nh3` 优先 / `bleach` 兜底），
`<script>` / `onerror=` / `javascript:` 全部被剥掉。**前端可以直接 `innerHTML`**。
**如果将来换抽取实现，这一步不能省** —— 文件内容是不可信输入。

### 2.4 `t_kb_upload_task` —— 异步上传任务

**干什么**：`POST .../documents?async=1` 会**毫秒级返回一个任务号**，真正的上传在后台跑。
这张表就是任务的落点，前端拿 `task_id` 轮询进度。

```sql
CREATE TABLE `t_kb_upload_task` (
  `id`            bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `task_id`       varchar(64)  NOT NULL                COMMENT '任务号（给前端轮询用）',
  `index_id`      varchar(32)  NOT NULL                COMMENT '目标知识库',
  `file_name`     varchar(255) NOT NULL                COMMENT '原始文件名',
  `size_bytes`    bigint       DEFAULT NULL            COMMENT '字节数',
  `md5`           char(32)     DEFAULT NULL            COMMENT '内容MD5',
  `storage_path`  varchar(500) DEFAULT NULL            COMMENT '已落的本地原文路径（失败时会删掉）',
  `uploader`      varchar(64)  DEFAULT NULL            COMMENT '上传人（业务用户ID）',
  `status`        varchar(16)  NOT NULL DEFAULT 'pending' COMMENT 'pending排队 / uploading上传中 / done成功 / failed失败',
  `file_id`       varchar(64)  DEFAULT NULL            COMMENT '云端文件ID（成功后回填，前端拿它去预览）',
  `error`         varchar(500) DEFAULT NULL            COMMENT '失败原因（给人看的）',
  `wait_parse`    tinyint      NOT NULL DEFAULT '1'    COMMENT '原样记录本次上传参数',
  `submit_index`  tinyint      NOT NULL DEFAULT '1'    COMMENT '原样记录本次上传参数',
  `skip_if_exists` tinyint     NOT NULL DEFAULT '1'    COMMENT '原样记录本次上传参数',
  `elapsed_ms`    int          DEFAULT NULL            COMMENT '上传耗时（毫秒）',
  `create_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_task` (`task_id`),
  KEY `idx_status` (`status`),
  KEY `idx_index_time` (`index_id`,`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='知识库异步上传任务';
```

**状态流转：**

```
pending ──→ uploading ──→ done    （file_id 回填，前端拿它去 /api/kb/files/{id}/text 预览）
                     └──→ failed  （看 error；本地已落的原文会被删掉）
```

> ⚠️ **服务重启会把"上传中"的任务标成 `failed`，并且不会自动重试。**
> 原因：上传链路（申请租约 → PUT → 登记 → 等解析）**不幂等**，而且中断时无法判断上次传到哪一步，
> 重试只会造重复文档。任务仍在表里能查到，但需要**人工重传**。

### 2.5 `t_chat_session` 新增的三列（L2 会话摘要）

不是新表，是给会话表加了 3 列，用来支撑"长会话也能记住前文"：

```sql
ALTER TABLE t_chat_session
  ADD COLUMN summary          mediumtext  COMMENT '会话摘要（L2）',
  ADD COLUMN summary_upto_seq int         NOT NULL DEFAULT 0 COMMENT '摘要已覆盖到第几条消息',
  ADD COLUMN summary_time     datetime    COMMENT '摘要生成时间';
```

| 列 | 作用 |
|---|---|
| `summary` | 这场会话**更早轮次**的浓缩（≤150 字）。只写"关注对象 + 固定叫法"，**不写时间口径、不写结论、不写数字** |
| `summary_upto_seq` | 摘要覆盖到第几条消息。★ **注入时【对话历史】只带 `seq_no` 大于它的轮次**，避免摘要与明细重复 |
| `summary_time` | 生成时间 |

**生成时机**：每 5 轮问答（可配 `SECRETARY_SUMMARY_EVERY`）触发一次，**后台异步**生成，不阻塞回答。
写回时用**乐观锁** `WHERE summary_upto_seq = <读到的值>`，防止同一会话并发摘要互相覆盖。

**★ 两道注入闸**（不是所有会话都会注入摘要）：

| 闸 | 条件 | 原因 |
|---|---|---|
| ① | `history_turns=0` | 调用方明确说"本轮不要记忆"，摘要不能绕过它溜进来 |
| ② | 会话总轮数 < `SECRETARY_SUMMARY_MIN_TURNS`（默认 6）| 短会话的 history 已经覆盖全场，注入是纯重复 |

没注入时 `/api/ask` 响应里 `summary_skip` **会写明原因**，排障先看它。

## 三、怎么建这些表

```bash
cd <项目根目录>
python -X utf8 tools/apply_kb_file_schema.py           # 建表 + 自检（幂等，可重复跑）
python -X utf8 tools/apply_kb_file_schema.py --check   # 只看现状、不建
```

脚本会：

1. 建 `t_kb_file` / `t_kb_file_page` / `t_kb_upload_task` 三张表（已存在就跳过）
2. 给 `t_chat_session` 补 `summary` / `summary_upto_seq` / `summary_time` 三列（已存在就跳过）
3. 打印自检结果

完整建库脚本（含 2.0 时代那批表）在工作区的 **`agent_data_建表.sql`**。

> ★ **不建表服务也能起来**：只是没有本地副本、没有预览（`/api/kb/files/**` 返 503，
> `/health` 里 `kb_files: false`）。**不会拖垮问答。**

## 四、几张表之间的关系

```
t_chat_session ──1:N──> t_chat_message ──1:1──> t_chat_query_trace ──1:N──> t_chat_trace_step
      │                                                 │
      │ (summary 三列)                                    └── 记一轮问答的口径与质量
      └──1:N──> t_long_term_memory（预留，代码未用）

t_kb_file ──1:N──> t_kb_file_page
（file_id 关联；不是外键，靠代码维护）

t_kb_upload_task ──(成功后)──> t_kb_file
（task.file_id = kb_file.file_id）
```

> ⚠️ 表之间**没有建外键**，全部靠代码维护一致性。原因：这些表要能独立重建/清理，
> 外键会让"清孤儿页""删测试会话"这类运维操作变麻烦。代价是**删数据时要自己记得连带删**
> （例如 `soft_delete` 必须连 `t_kb_file_page` 一起删，否则留孤儿页）。

## 五、通用约定（改这些表前要知道）

| 约定 | 说明 |
|---|---|
| **`deleted_flag`** | 所有业务表都有，**逻辑删除**，查询时必须带上 `deleted_flag = 0`。<br>⚠️ 例外：`t_power_work_order` 是 `varchar(2)`，要写 `deleted_flag = '0'` |
| **字符集** | 统一 `utf8mb4` / `utf8mb4_general_ci`。<br>⚠️ 与 `dlj_data` 不一致时跨库 JOIN 会报 `1267 Illegal mix of collations` |
| **时间** | 一律 `datetime`，`CURRENT_TIMESTAMP` 默认；更新时间用 `ON UPDATE CURRENT_TIMESTAMP` |
| **`t_kb_file.md5`** | 落盘目录名就是它（`{root}/{index_id}/{md5}/{文件名}`）—— 上传前就能算出来，天然去重、失败好清理 |
| **不要写 `ai_data` / `dlj_data`** | 只读。表结构由维护方改 |

## 六、排障速查

| 现象 | 查什么 |
|---|---|
| 预览 404 | 看 `t_kb_file.origin`：`console` 说明没本地副本（正常）；`api` 且有 `storage_path` 却 404 → 磁盘文件丢了 |
| 一直"正在提取" | 看 `extract_status` 是否卡在 `extracting`；服务启动会自动把未完成的重新排队 |
| 上传任务查不到 | 任务号只由上传接口返回；服务重启会把中断的标 `failed`（仍在表里）|
| 摘要没注入 | 看 `/api/ask` 响应的 `summary_skip` |
| 磁盘一直涨 | 删除文档**默认保留磁盘原文**。清孤儿文件：`python -X utf8 secretary/kb_store.py --purge` |
