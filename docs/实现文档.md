## 1. 要做什么

后端服务 + 本地演示页面：输入一条「上游信息补全后的问题（时间与地点已明确）」，模型**自主**决定查哪些表、怎么算、要不要查知识库理解口径，取数后给出**简短回答**，并把**每一步工具调用**结构化成可审计的轨迹（给右栏）。

## 3. 架构

    浏览器页面 127.0.0.1:8200（左栏回答 / 右栏轨迹）
       │  POST /api/ask {question}
       ↓
    server.py（标准库 http.server，零额外依赖）
       ↓
    agent.py：模型自主循环（步数不限）
       ├ kb_search(query, top_k)      百炼知识检索 → 切片（术语/口径/背景）
       ├ list_tables(keyword)         业务库有哪些表
       ├ describe_table(table)        表字段与注释
       └ run_sql(sql)                 只读取数
       每步写入 trace：{seq, tool, args, result, ms}
       ↓
    {answer, trace, model, elapsed_ms}

## 4. 工具契约

| 工具 | 参数 | 返回 |
|---|---|---|
| kb_search | query, top_k=5 | nodes[]: {score, title, content(截断), doc_name} |
| list_tables | keyword 可选 | tables[]: {name, comment, rows} |
| describe_table | table | columns[]: {name, type, nullable, comment} |
| run_sql | sql | {columns, rows, row_count, sql, error?} |

## 7. 测试方案

- **题库**：上游《通用语义知识库》标准问法，取 12 条（综合/预算/项目/治理/主数据/对比各覆盖）+ 3 条超范围（酒店/集团/用电）。
- **判定三类**（人工逐条核对，落盘）：
  1. 对：数字与口径都对（拿现有系统 facts 或直接查库核对）；
  2. 错：数字错、口径错、或答非所问；
  3. **未查库就答**：trace 里 run_sql 次数为 0 却给出了结论 —— 这一类最严重。
- **双模型**：qwen3.8-max 与 qwen3.8-flash 各跑同一批题，比 4 项：答案正确率、**工具选择是否合理**、**子问题拆分是否完整**、耗时。
- 落盘：output/test_report_<model>.md 与 .json。

## 8. 已知风险（先说清）

1. **口径知识库还没建** —— 现在这份业务知识库检索质量差（实测"预算执行率的定义"返回 0 条，"项目执行率怎么算"命中一条 score 0.28 的无关切片）。这会直接拖低准确率，报告里会标注"口径库未接入"。
2. 模型可能不查库就答 —— 用"未查库"自动打标 + 单独统计。
3. 133 张表全给模型，靠它自己筛；表名与注释是它唯一的线索。
4. 只读闸对 WITH 写法可能误伤 —— 暂不支持 CTE，遇到就报错让模型改写。
