## 任务一：让模型知道去哪查（表 / 字段字典）

### 实际情况（怎么样）

| # | 量到的事实 | 出处 |
|---|---|---|
| 1 | list_tables 暴露 dlj_data 全部 **133 张表**，混着 t_power_area_bak_20260901、t_power_work_order_copy1 / copy2、t_power_work_order_ago_img_bak_20260902 等备份与废弃表 | tools_db.list_tables 当前实现 |

| 3 | **摸底类（list_tables + find_column + describe_table）= 69 次 = 44%**，不产生任何答案数据 | 同上 |
| 4 | 字典两张表：ai_table_metadata **16 行**、ai_column_metadata **158 行**（覆盖 15 张表），就是「AI 该看哪些表、哪些字段」 | ai_data 库实查 |

| 9 | 字段覆盖率：t_power_work_order 12/77、t_power_company 13/34、t_power_company_assessment 23/34、t_power_station_score_detail 8/22、t_power_company_budget_result 7/18 | 同上 |

第 3 条是关键：**44% 的模型往返花在"找表"上，不是花在取数上。** 同时它也是 e2e 里 3 次答"查不到"的原因（猜错了表）。
第 9 条要逐表确认：少列多数是刻意降噪，但**漏掉的字段会让复杂问题写不出 SQL**。

### 建议（具体实施方案）

**新增 `secretary/semantic.py`** —— 进程启动时读一次 ai_* 两张表进内存（16 + 158 行，一条 SQL），提供 5 个函数：

| 函数 | 作用 |
|---|---|
| `allowed_tables()` | 白名单表名集合 |
| `table_menu()` | 注入 system prompt 的表级目录文本（表名 + 中文名 + 一句用途，16 行） |
| `columns_of(table)` | 该表字段清单（中文名 / 类型 / 真值示例） |
| `find_columns(keyword)` | 只在字典内搜字段 |
| `is_allowed(table)` | run_sql 前的表名校验 |

**改 `secretary/tools_db.py`**（4 处）：

| 函数 | 改成 |
|---|---|
| `list_tables(keyword)` | 只读 semantic 字典，不再查 information_schema |
| `find_column(keyword)` | 同上 |
| `describe_table(table)` | 先 is_allowed 校验；字段取自字典，**字典里没有的字段回退到真库 DESC**（否则漏字段会写不出 SQL） |
| `run_sql(sql)` | 正则抽出 FROM / JOIN 后的表名，逐个 is_allowed；不通过则返回「表 X 不可用；可用表：…」，让它自己改 |

**改 `secretary/agent.py`**（2 处）：

| 位置 | 改成 |
|---|---|
| SYSTEM | 加一段表级目录（16 行，约 600 token）；第 3 条底线从"不确定就先 find_column / list_tables"改成"数据在这些表里，不确定字段再用 find_column" |
| TOOLS | list_tables / find_column 的 description 从"全局搜"改成"在业务字典内搜" |

**新增 `secretary/语义层补充.md`**：字典里缺的表/字段在这里登记，semantic.py 读它并**与 ai_* 合并（只加不改）**。同时在文档里列出"建议补进 ai_* 的行"，交同事入库。

**不做什么**：不写数据库（ai_* 只读）；不改 SQL 安全闸；不改循环逻辑；不加第 6 个工具；空表不删，标注「本表无数据，线损看 t_power_push_city_month_summary」。

### 预计成功

| 指标 | 现在 | 预期 | 依据 |
|---|---|---|---|
| 摸底类调用（27 题合计） | 69 次 | ≤ 15 次 | 目录替代了 4/5 的摸底场景 |
| 摸底占比 | 44% | ≤ 10% | 同上 |
| 复杂题（16 次工具那道） | 16 次 / 39.5 s | 约 9 次 / 约 22 s | 该题摸底约占 7 次，每次往返约 2.5 s |
| e2e 里"查不到" | 3 次 | 0 次 | 3 次都是猜错表（缺汇表）导致 |

### 验收标准

1. 27 题重跑，摸底类调用合计 **≤ 15 次**（脚本按 trace 计数，落盘 output/）。
2. run_sql 引用字典外的表 → 被拒，且模型下一轮自行改用字典内的表，最终答案仍对。
3. 27 题正确率 **不低于 15 对**（现在 15 对 / 6 半对 / 5 错）。
4. 每次回答的 trace 里出现的表名，**100% 属于白名单**（脚本校验）。

## 任务二：复杂问题的串行（主战场）

### 实际情况（怎么样）

| # | 量到的事实 | 出处 |
|---|---|---|
| 1 | 复杂题实测：**16 次工具、循环 39.5 s**，一拍一拍串行走 | 页面实测（deepseek-v4-pro） |
| 2 | 模型每次往返 **1.6–2.5 s**，数据库每次 **0.26 s**。耗时 = 往返次数 × 2 s | 27 题 trace 统计 |
| 3 | agent.py 拿到同一轮的多个 tool_calls 是 **for 循环串行执行**，没有并发 | agent.py 第 169 行起 |
| 4 | 已排除：上下文变长导致每轮变慢（每题前半段 vs 后半段 +10% / +0% / +45%，无一致趋势） | 逐轮 model_ms 统计 |
| 5 | 已排除：换更快的模型（qwen3.8-flash 同题工具调用数翻倍 22 次 vs 7 次，耗时 33.6 s vs 12.7 s） | output/test_raw_qwen38-*.json |
| 6 | 复杂题的数据点大部分**互相独立**（预算一张表、工单状态另一张、六指标在汇总表），本可以一次发出，现在被拆成 16 拍 | 该题 trace 逐条看 |

### 建议（具体实施方案）

**改 `secretary/agent.py`**（3 处）：

| 位置 | 改成 |
|---|---|
| 第 169 行的 for 循环 | 用 ThreadPoolExecutor（最多 4 并发）执行**同一轮**的 tool_calls；结果按原顺序回灌 messages（tool_call_id 必须一一对应，顺序不能乱） |
| SYSTEM | 加一句：互不依赖的查询（不同表的指标）放在同一条消息里一次发出 |
| trace 每条 tool 记录 | 加 `round` 字段（第几轮）→ 页面能看出"这一轮一次发了 N 条" |

**不加 run_sql_batch 这类新工具**：加了等于替模型决定"先规划再执行"，与"不固化流程"冲突。先看它会不会批量发；确实不会再加。
**不改**：工具签名、数据库、循环的收手逻辑、零工具拦截。有依赖的查询仍串行——那不追求并行。
**并发安全已具备**：tools_db 的连接是按线程存的，天然支持多线程。

### 预计成功

| 指标 | 现在 | 预期 | 依据 |
|---|---|---|---|
| 复杂题往返次数 | 16 次 | 6–8 次 | 摸底砍掉约 7 次，独立查询合并再省 2–3 次 |
| 复杂题总耗时 | 39.5 s | 12–18 s | 往返数 × 2 s |
| 简单题 | P50 约 10 s | P50 ≤ 6 s | 摸底砍掉后 2–3 次往返 |

### 验收标准

1. 3 道复杂题里，**至少 1 道**的 trace 出现"同一轮 ≥ 2 条工具调用"。
2. 复杂题往返次数 ≤ 实际查询条数 × 0.6 + 2。
3. 3 道复杂题 **P90 ≤ 20 s**（不含外置补全）。
4. 27 题正确率不下降（≥ 15 对）。
