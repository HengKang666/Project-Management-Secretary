# 项目管理秘书 · 架构图（Mermaid）

> 完整链路：**语音 → 转写 → 上游信息补全（机构名纠错 + 统计时间）→ 模型自主任循环（问题补全 → 查口径 → 取数 → 作答）→ 回答 → 缺口沉淀**。
> 分工：**上游外置工作流负责机构名自动纠错与统计时间；问题补全由本服务做**（用知识库里的补全规则与术语词典）。
> 源码就是这个文件，支持 Mermaid 的编辑器（VSCode / Typora / 语雀 / GitHub）能直接渲染。

## 各阶段实测（本地样例音频 82 KB）

|---|---|---|---|
| ① 取上传凭证 | GET | 200 | 202 ms |
| ② 上传到 OSS | POST | 200 | 270 ms |
| ③ 提交转写任务 | POST | 200 | 177 ms |
| ④ 轮询（RUNNING） | GET | 200 | 146 ms |
| ④ 轮询（SUCCEEDED） | GET | 200 | 190 ms |
| ⑤ 下载转写结果 | GET | 200 | 155 ms |
| **语音合计** | | | **≈1.1 秒** |

| 环节 | 实测耗时 | 说明 |
|---|---|---|
| **本服务全程**（含问题补全） | **5.8 – 11.1 秒**（16 道「信息补全后」的口语问法） | 平均约 8 秒；复杂题最长 13 秒 |

| 其中 run_sql | 0.1 – 0.3 秒 / 次 | 白名单内的只读查询 |

## 说明

1. **代码里的业务规则 = 0 条**：分支只有"有没有 tool_calls"和"有没有用过工具"。
2. **表/字段/口径全在外部数据里**：业务字典 `ai_data` 5 张表（26 张表 / 334 字段 / 18 条指标口径）+ 知识库 `r57xtq9ypm`（补全规则 + 业务术语词典）。
3. **模型可换**：页面下拉 26 个模型（通义 / DeepSeek / Kimi / GLM / MiniMax），换模型不用重启服务。
4. **每一步都可审计**：语音五阶段、循环里的每次工具调用（含决定发几条、哪一轮、耗多少毫秒），都留在 trace 里，页面可逐层展开。
5. **两个机制**：
   - **同一轮并发**：模型同一条消息里发的多个查询由线程池并发执行（实测复杂题 16 次串行往返 → 3 轮）。
   - **缺口清单**：答"查不到 / 未核实"的问题自动落 output/gaps/gaps.jsonl，GET /api/gaps 可导出 —— 打地鼠的正确出口是**把缺口交回上游**，不是加关键词。
6. **页面入口**：问答页 http://127.0.0.1:8200/ ｜ 语音页 http://127.0.0.1:8200/asr （可加 ?run=sample 一键跑示例音频）
