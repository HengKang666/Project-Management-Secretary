## 二、大模型怎么决策

**代码里没有任何业务判断**：不判断问题类型、不选表、不选口径。所有分支都由模型在循环里产生。

| 它面对的 | 它自己决定 |
|---|---|
| 问题里有几个子问题 | 拆成 ①②③，还是一次答完 |
| 数据大概在哪 | 先 kb_search 找口径，还是先 find_column / list_tables 找表 |
| 要查几次 | 查一次够不够；要不要换一张表再查 |
| 数字怎么算 | 按口径库给的公式算，还是改用别的聚合 |
| 够不够答 | 收手作答，还是继续查 |
| 答不了 | 说"查不到"并说明查了什么；范围外直接拒答 |

系统提示只给 4 条底线（不是流程）：
1. 先用知识库弄清术语/口径/统计范围；
2. 业务数字必须来自 run_sql，知识库的数字不当答案；
3. 不确定在哪张表就先 find_column / list_tables / describe_table，不要凭表名猜；
4. 中文作答，先结论后数字，每个数字带单位和口径，多子问题用 ①②③，160 字内；
5. 排名/极值/计数交给数据库算（ORDER BY / LIMIT / COUNT / GROUP BY），不要把上万行取回来自己看；同一张表别反复 describe。

## 三、可以调用的工具（5 个）

| 工具 | 参数 | 返回 | 什么时候用 |
|---|---|---|---|
| **kb_search** | query, top_k | 按相关度排序的文档切片（口径/业务背景） | 先弄清术语、指标口径、统计范围 |
| **find_column** | keyword | 表名 + 字段名 + 类型 + 中文注释（最多 80 条） | 不知道"这个数据在哪个字段/哪张表"，全局搜 |
| **list_tables** | keyword 可选 | 表名 + 中文注释 + 估算行数 + 更新时间 + **用途标记** | 找表；带"备份/暂存，勿当数据源"的表不要用 |
| **describe_table** | table | 全部字段（名/类型/是否可空/注释）+ 前 2 行样本 | 看一张表的完整结构 |
| **run_sql** | sql | 列名 + 行数据 + 行数（只读、限 200 行、25 秒） | 真正取数（唯一的数据来源） |

## 四、复杂问题怎么处理

| 形态 | 处理方式 |
|---|---|
| **多子问题**（"预算多少？执行率多少？成效如何？"） | 模型自己拆成 ①②③，各自查各自的表，逐条作答 |
| **跨表/跨源**（预算要 allocation，成效要 assessment） | 多次 run_sql，各自带口径 |
| **知识 + 数据混合**（"线损率是什么、今年多少"） | 先 kb_search 拿口径定义，再 run_sql 取数 |
| **找不到表**（"这个数据在哪"） | find_column 搜字段 → describe_table 看结构 → run_sql 验证 |
| **同一张汇总表多指标** | 系统提示要求"一并给出"，避免只答一个（例：202609 那一行同时有 6 项指标） |
| **口径有陷阱**（当月/累计、版本重复） | 口径库里写明规则（summary_type 两行、is_new 去重），并附真实现象表 |
| **答不了** | 四类：知识库没这条 / 指标库没这统计 / 粒度不支持 / 超范围 —— 各自话术，且都落缺口 |
| **不调工具就答** | 提醒一次 → 仍不调 → **拦下**，返回"未核实，不予作答"，被拦下的原文记进 trace |
| **查太久收不了手** | 剩 3 步开始，每一步追加提醒"你还有 N 次机会，请尽快收手"（服务层注入，不是业务规则） |

## 四之二、换问题实测（10 个多样问题）

| # | 问题 | 结果 | 步数/耗时 |
|---|---|---|---|
| 1 | 4 个供电公司今年的售电量和线损率 | ✅ 4 家全给，带 upCurrentMonth 口径 | 6 步 / 15s |
| 2 | 今年线损率最高的台区 | ⚠️ 说"查不到"，理由充分（台区表无统计时间字段、推送表为空） | 11 步 / 22s |
| 3 | 今年预算最高的供电所 | ✅ 府河供电所 523,790.55 元 | 5 步 / 8s |
| 4 | 停电时长最高的供电所 + 另 5 项 | ✅ 环潭 6.60 小时/户，另 5 项一并给出 | 8 步 / 15s |
| 5 | 审批通过未开工的工单 | ⚠️ 说"查不到"，指出库内工单最新到 2026-08 | 4 步 / 10s |
| 6 | 被驳回的工单及原因 | ✅ 16 个，原因分三类 | 5 步 / 9s |
| 7 | 台区总数 + 线损率>5% 的个数 | ✅ 20388 个 / 0 个（最大 4.94%） | 6 步 / 9s |
| 8 | 意见工单最多的供电所 | ✅ 神农供电服务站 17 件（加收手提醒后才答出来） | 6 步 / 27s |
| 9 | 公司资质材料在哪张表 | ✅ 明确说库里没有 | 4 步 / 5s |
| 10 | 随州市 2026 年 GDP | ✅ 明确说没有，并说明知识库只有 2025 年值 | 3 步 / 5s |

**步数限制已放开**：原先是硬上限 12 步。现在**不设上限**，改为从第 15 步起每 5 步软提醒一次"已有足够数据就立刻给结论"。实测："情况怎么样"10 步 28.9 秒答完，工单分档与六项指标全部与真值一致。

## 五、表结构怎么展示（现状与优化）

**现状**
- 133 张表 / 1956 个字段，模型通过 information_schema 拿元数据；
- list_tables 一次最多给 150 张（带中文注释和估算行数）；
- find_column 全局搜字段（最多 80 条），解决"这个字段在哪张表"；
- describe_table 给完整字段 + 2 行样本。

**已做的优化**
1. **用途标记**：表名含 _bak_ / _copy / stg_ / _ago_img_ 的标为"备份/暂存，勿当数据源"；t_power_push_* 标"中台推送结果"；ai_* 标"非业务事实源"。
2. **《数据地图》进知识库**：133 张表按主题分组 + 上一版服务 29 条白名单查询实际访问的表 —— 模型可以先"读地图"再查表。
3. **口径库写明易错字段**：预算表的 version/is_new 去重、month_loss_rate 与 loss_rate 的区别。

**还可以再优化**
1. 加一个 table_profile 工具：一次给某表的实测行数 + 主键 + 时间字段 + 关键字段取值分布（枚举含义），让模型少猜；
2. 把"表 ↔ 业务对象"的关联关系补全（你的口径文档第 11 节已有骨架）；
3. 口径库继续按"现象 + 范例"补，每踩一个坑就补一条。

## 六、回答格式规范

- 第一句给结论，后面分点给数字；
- 每个数字带单位；并注明口径（时间范围 + 统计范围）；
- 多子问题用 ①②③；
- 同一张汇总表里的其它相关指标一并给出；
- 查不到就说查不到，并说明"我已经查了什么"；
- 不写客套话，总长 160 字以内。
