# 字典缺口清单（其余定时技能维度）

> 起因：已补好的只有【审批待办】一个维度。按同一套路过其余技能时，实测条数仍不稳：
> `flow-monitor` 两次跑出 **0 / 6**、`progress-alert` 两次标题词不同（"钱花了没动" / "执行进度异常"）、
> `risk-control` 恒 0（需确认口径）。查字典后确认：**是维度标注缺失，不是模型问题。**

## 一、实测证据（同一天、同一账号、连打两次）

| 技能 | 第 1 次 | 第 2 次 | 用的取数 |
|---|---|---|---|
| `flow-monitor` | 0 · "今天无项目逾期" | **6** · "今天有 6 个项目比同类在办偏久" | 一次按**逾期**、一次按**同类 P75 偏久** —— 两次换了维度 |
| `progress-alert` | 7 · "钱花了没动" | 7 · "执行进度异常" | 计数同、**结论维度名不同** |
| `risk-control` | 0 | 0 | 用 `DATE(update_time)=今天` 判"当天新增申请" —— 语义可疑 |

## 二、字典里缺的（逐条带字段证据）

| # | 缺什么维度 | 证据 | 影响 |
|---|---|---|---|
| 1 | **状态分组维度** | `ai_column_metadata` 里 `t_power_work_order.work_status` 的 **`is_dimension=0`**（被标成非维度）；「执行阶段」(3/6/7)、「在审批中」、「草稿」这些**分组**没有任何标注 | 各技能每次自己决定哪些状态算"执行阶段"→ flow-monitor 摇摆 |
| 2 | **维度词没进同义词** | `ai_column_synonym` 里查：**逾期 / 偏久 / 执行阶段 / 钱花了没动 / 可用余额 / 计划完工 / 停留天数 / 状态变更时间 全部没有**（只补过"待办"那一批 15 条） | 换个问法就认不出对应字段 |
| 3 | **停留天数的起算点** | 工单表登记了 `create_time`(创建时间) 与 `update_time`(更新时间)，但**没有一处说"停留天数 = 系统当天 − 进入当前状态的时间"**；实测模型拿 `create_time` 当停留起算 | 同一技能两次算出不同天数（曾出现同一单 152 / 158 / 166 天） |
| 4 | **计划完工日为空这件事** | `plan_end_time`(计划结束时间) 已登记，但**没标"实测 99% 为空、不能用于判逾期"** | 模型有时用它判超期、有时改用 P75 → 摇摆 |
| 5 | **可用余额是哪个字段** | 三张表已登记：`t_power_company_budget_allocation`(预算配置表) / `t_power_company_budget_result`(预算分配结果表) / `t_power_company_budget_profile`(基础画像表)，但**"该所当年可用余额"这个维度没写清落在哪张表哪个字段** | 资金合理性判断没有稳定取数 |
| 6 | **状态最后变更时间：库里根本没有** | 全字典搜 `%status_time%` / `%change_time%` / `%变更时间%` **无命中** | 技能文档要求"没有就写无法判定"——这条是对的，但字典里也该**显式说明该维度缺失**，否则模型会拿别的字段硬凑 |

## 三、补法（同一套路，不写死查询）

1. **状态分组做成一等维度**：`work_status` 的 `is_dimension` 改 1；并新增**状态分组**维度（草稿 / 在审批 / 执行阶段=3,6,7 / 已完成 / 已驳回取消），把分组名写进 `business_desc` + 同义词。
2. **同义词补齐**：逾期、偏久、超期、执行阶段、钱花了没动、可用余额、计划完工、停留天数、状态变更时间 → 各自落到承载字段。
3. **时间语义写清**：`create_time` / `update_time` / `plan_end_time` 各自标注"能不能当口径"，并写明「停留天数起算点」该用哪个（没有状态变更时间时，明确写"只能用 X，且要说明这是近似"）。
4. **缺失字段显式登记为缺口**：状态最后变更时间——在字典里写清"该维度当前无数据源"，让模型照实说"无法判定"，而不是拿 `update_time` 硬凑。
5. **可用余额**：把维度词落到具体表+字段（需业务确认是按配置表还是结果表）。

## 四、验收判据（每个技能都要过）

同一天、同一账号、同一个技能，**连打 5 次标题必须都得到同一个数、同一句话**；
且与直接跑该技能的判据查询结果一致。达不到就继续查字典，不改代码糊过去。

# 四、新根因（字典补完仍不稳的原因）

**这两个技能的"标题"本身没定死报哪个维度。** 技能文档里列了 4 个维度——
「哪些落后 / 哪些逾期 / 哪些年内完不成 / 卡在谁那里」，
但标题只有一行，**没写这一行取哪一个维度**。于是模型每次自己挑：
一次挑"逾期"（0 条）、一次挑"同类偏久"（2 条）、一次挑"钱花了没动"（7 条）——都对，但每次不一样。

对比 `approval-role` 为什么稳：它的技能文档把标题写死了——
「截至 X 日，您这一级有 N 张待处理、合计 X 万元，其中积压 N 张」——**只有一个维度**。

## 要补的是"标准"，不是代码

给每个定时技能在技能文档里补**一句「标题判据」**：
`标题 = 取哪个维度 + 阈值 + 一句话模板`。例如
- `flow-monitor`：标题取「停在我范围内的项目里，状态停留超过该环节阈值（一般30/审批90天）的条数」；
  没有才退回「同类偏久」；两者都没有才写「今天无项目逾期」。
- `progress-alert`：标题取「钱花了没动」条数（已发生金额本所前 10 且状态停 3/6 超 90 天）；
  没有才退回「同类偏久」；都没有才写「今天无进度异常」。

**优先级链写进文档 = 标题唯一**，不写死任何 SQL、不改代码。
