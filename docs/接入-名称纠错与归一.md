# 接入：名称纠错与归一（阶段①的「字面」部分）

> 2026-09-17 接入。**零第三方依赖**，只用 Python 标准库。

## 一、为什么接在这里

本服务原有五段流程，其中

> **① 信息补全 ｜ 上游（外置） ｜ 无，/api/ask 只接一个 question**

这一步一直是空的、且只规划了「补统计时间与地点」。本次补的是**字面**：
把说错的字改对、把只说半截的名称补成库里的标准名。

**必须排在 `complete_question()` 之前**：

```
「环谈供电所的台区线损」
  → 不改字：拿「环谈供电所」去检索知识库 → 检索不到 → 补全规则命中不了
  → 改对字：检索「环潭供电所」→ 命中补全规则 → 才可能补成标准问题
```

字都没改对，后面的检索、补全、写 SQL 全是白费。


相对本服务原有的「补全 2~3 s + 查数 4~17 s」，占比可忽略。

## 四、⚠️ 合成名：库里没有这个精确名

`公家棚 → 龚家棚台区`，但**「龚家棚台区」这五个字在库里不存在** ——
库里是「龚家棚八组」「龚家棚村3#台区40123」等 15 个。

所以 `name_fix.fix()` 会额外返回一句 `hint`，`agent.py` 把它附在问题后面：

> 【名称归一说明】下面的名称是按「地名层」归一的合成名，**库里没有这几个字的精确名**，
> 查库请用 LIKE 前缀匹配，不要用等号：龚家棚台区（按前缀 龚家棚% 查，共 15 个同名台区）

**不加这句的后果**：模型拿「龚家棚台区」做等值匹配 → 一条都查不到 → 答「暂无数据」，
而用户会以为真的没数据。**比不纠错还糟。**

## 五、开关与排障

| 做法 | 效果 |
|---|---|
| `set SECRETARY_NAMEFIX=0` | 整体关闭这一步（改回原行为，不用改代码） |
| `python name_fix.py` | 单独自测（不连库、不调模型） |
| 页面右侧 trace | 多一条 `namefix`，能看到纠错前后与每条改动依据 |

**设计原则：这一步失败不影响主流程。**
库加载失败或运行异常，`fix()` 一律返回原文 + `used=False`，
只在控制台打一行 `[namefix] ...降级`，主链路照常跑。

## 六、零依赖是怎么做到的

拼音原来靠 `pypinyin`（纯 Python，但仍是第三方包）。本服务要求「标准库实现」，
所以把「汉字 → (声母, 韵母)」**离线导出**成 `libs/name_correction_lib/data/pinyin_table.csv`
（2 万字 / 206 KB），运行时只查表。

**表的精度靠「语境投票」**：先给每个汉字填单字默认音，再用**库内真实名称**按词算一遍音投票覆盖 ——
多音字（畜牧 chù/xù、模板 mú/mó、支行 háng/xíng）按它在业务名称里的实际读法定音，
所以和索引里预计算的拼音码口径一致（实测 **99.49%** 一致，剩 0.51% 是多音字，影响可忽略）。

验证：屏蔽 `pypinyin` 后引擎照常工作，召回率不变（台区 99.7%、误改 0）。

## 七、换成别的领域

`libs/name_correction_lib/data/` 下 8 个 CSV 就是全部知识，
**必改的是 `catalog.csv`**（换成你的名录）。换完要重跑两个生成脚本：

| 脚本 | 作用 | 什么时候跑 |
|---|---|---|
| `tools/18_build_pinyin_table.py` | 生成 `pinyin_table.csv`（含语境投票） | **换名录后必须跑** |
| `tools/15_add_area_core.py` | 生成 `area_core.csv` 的台区核心码 | 换了台区名后跑 |

> 三个文件（`pinyin_table.csv` / `catalog.csv` / `area_core.csv`）的**码口径必须一致**。
> 不一致的表现是「看着像却匹配不上」—— 不报错，只是匹配率悄悄下降。
