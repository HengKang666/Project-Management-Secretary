# 微调 / LoRA 方案讨论（暂不动代码）

> 问题：能不能把知识库的知识用 LoRA 训进 qwen3.6 之类的模型，让它不查知识库也能判断？数据怎么收集？能不能达到效果？

## 0. 先给结论

1. **"训事实"这条路不划算**：有实证表明 LLM 通过微调很难学会新事实，而且一旦学进去，**幻觉倾向会线性上升**。用 LoRA 塞事实 ≈ 花钱买幻觉。
2. **"训行为"这条路值得走**：工具调用纪律（必须先查再答）、收手能力、输出格式与口径纪律 —— 这些是行为，微调是最合适的工具，而且正是我们实测出来的两个硬伤。
3. **"完全不查知识库"不可取**：可以做到"少查也答对大部分"，但表结构/口径一变就翻车，而且失去可审计性。
4. **数据不用另找 —— 我们已经在生产训练数据了**：每一次问答都是一条 tool-use 轨迹，现在只差把 trace 落盘。

## 1. 先分清三类"知识"（决定命运）

| 类型 | 例子 | 能不能训进权重 | 为什么 |
|---|---|---|---|
| **稳定事实 / 映射** | 工单状态码 0–9 的含义、字段名、表名、预算执行率 = 执行金额 ÷ 预算金额 | ✅ 可以，而且应该 | 不常变，属于"领域语言"，是权重擅长的事 |
| **会变的数值** | 2026 年 9 月全市线损率 2.61% | ❌ **绝对不能** | 下个月就过期；训进去只会教它编 |
| **结构与关系** | 哪个指标在哪张表、表之间怎么关联 | ⚠️ 能提高"起手命中率"，但**必须保留检索兜底** | 表结构一变就全废；权重能记住的条数有限 |

## 2. 实证（不是拍脑袋）

- **Ovadia et al.（arXiv 2312.05934，Fine-Tuning or Retrieval?）**：在多种知识密集型任务上对比无监督微调与 RAG，结论是 **RAG 稳定优于微调**，无论是要注入"训练中见过"还是"全新"的知识；LLM 通过无监督微调**很难学会新的事实**。
- **Gekhman et al.（arXiv 2405.05904，Does Fine-Tuning LLMs on New Knowledge Encourage Hallucinations?）**：微调引入的新事实**学得明显更慢**；而且当这些样本最终被学会时，模型的**幻觉倾向线性增加**。结论是 LLM 的事实知识主要来自预训练。

→ 这两篇合起来说明：**把知识库的事实塞进权重，性价比低且有副作用。**

## 3. 微调应该干什么：训行为，不训事实

三个最适合微调、且正是我们实测短板的东西：

| 训什么 | 现在的实测问题 | 为什么适合微调 |
|---|---|---|
| **工具调用纪律** | max 有 3/15 ~ 4/15 一次工具都不调就编，还谎报"已查询数据库" | 这是行为模式，SFT / DPO 最擅长 |
| **收手能力** | flash 15 题里 11 题跑满 12 步不给答案 | 同上，行为 |
| **输出与口径纪律** | 有时漏掉单位、漏掉"时间范围"、只答一个子问题 | 格式与风格，微调的强项 |
| 附带的：**领域术语归一** | "三公经费""线损"要映射到标准字段/指标名 | 半事实半语言，可以训 |

**架构不变**：微调后的模型 + 知识库检索 + 只读 SQL。微调让它**少犯错**，不是让它**不查库**。

## 4. "不基于知识库也能判断"的边界（逐项回答）

| 要它判断的事 | 微调能做到吗 | 结论 |
|---|---|---|
| 该查哪张表 | 能显著提高命中率 | 但表结构/口径一变就退化 → **保留一次 kb_search 兜底**（几百毫秒，成本几乎为零） |
| 这个数是多少 | **不可能，也不该** | 数据是动态的，必须查 |
| 这条口径对不对 | 能记住常见口径 | 新口径或改口径仍必须走文档，不可能每次重训模型 |
| 该不该拒答 | 能训得更好 | 值得训：超范围 / 库里没有 / 粒度不支持，三类话术 |

**一句话**：可以做到"少查知识库也答对大部分"，但"完全不查"会在数据变化和新问法上翻车，而且丢掉"每个数字可追溯"这条底线。

## 5. 如果目标其实是"内网不能连百炼"

那也不该把知识训进权重，而是：**本地模型（Qwen3.6-27B / 35B 这类可自部署的）+ 本地向量库（放同一批口径文档）+ 只读 SQL + 行为微调**。
即：RAG 管事实与时效，语义层/口径文档管口径，微调管行为 —— 三件事各归各位。

## 6. 数据怎么收集（核心可操作部分）

### 6.1 关键洞察：训练数据已经在生产了

现在每一次问答都会产生一条完整轨迹：

    问题 → kb_search / find_column / describe_table / run_sql（含真实 SQL 与返回）→ 最终回答

这正是标准的 **tool-use SFT 轨迹**。现在只缺一件事：**把 trace 落盘**（目前只在响应里返回给前端，没有存成数据）。

### 6.2 四类数据来源

| 来源 | 价值 | 冷启动规模（经验值） |
|---|---|---|
| **真实日志**：页面/上游问过的每一问 + 完整轨迹 + 人工判定 | 最高（真实分布） | 几十 ~ 几百条 |
| **上游标准问法 55 条 × 变体**：模板已有，每种扩 5–10 种说法 | 高，专治"换个说法就崩" | 300–500 条 |
| **口径库 / 数据地图反推合成**：每条指标口径造 3–5 个"该查它"的问题；每张表造"哪些问题会用到它" | 覆盖面均匀、可控 | 数百条 |
| **负样本**（最容易被忽略、也最治病） | 极高 | 每类 100–300 条 |

### 6.3 负样本要专门造（这一类决定上线质量）

| 负样本类型 | 期望行为 |
|---|---|
| 超范围问题（酒店入住率 / GDP / 天气） | **直接拒答，不调工具** |
| 库里确实没有的数据 | 查证后说"没有"，并**说明已经查了什么** |
| 口径陷阱（当月 vs 累计、预算表版本重复） | 选对口径并写明 |
| **偷懒不查就答** | 被纠正 —— 用现在的拦截逻辑可以自动生成"错误答案 + 纠正"配对 |
| SQL 写错列名 | 看错误信息自我改写（这类轨迹现在天然存在） |

### 6.4 三种数据格式与预期

| 格式 | 治什么 | 量级（经验值，非本机实测） |
|---|---|---|
| **SFT 轨迹**（多轮 tool-calling，直接吃 OpenAI tools 格式） | 工具调用 + 输出格式 | 500–2000 条通常有明显改善 |
| **工具调用专项**（只保留"决定调什么工具、参数怎么写"那一步） | 选工具、写参数 | 几百条即可见效，最省 |
| **DPO 偏好对**（一条"先查库答对"的好轨迹 vs 一条"不查就编"的坏轨迹） | 专治不查就编 | 几百对 |

### 6.5 标注要求（缺一不可）

1. 每条样本要有 **ground truth**：关键数字的真值（直接查库核对，不能靠模型自评）；
2. **口径标注**：时间范围、粒度、来源表；
3. **判定标签**：对 / 错 / 未查库 —— 这三类我们报告里已经在做，可以直接复用；
4. 训练集与评测集**必须分开**，评测集要留"训练时没出现过"的问法。

## 7. 我建议的顺序

1. **现在就攒数据（零成本）**：trace 落 JSONL；用页面把 55 条标准问法 + 变体跑一遍，人工判定后入库。攒数据不影响任何现有逻辑。
2. **先训行为，不训事实**：第一版只训"工具调用纪律 + 收手 + 格式带口径"。
3. **先固定评测集再开训**：比如 60 题（6 个域 + 4 类拒答 + 口径陷阱），记录当前 max / flash 的成绩；训完在**同一个集子**上比，才说明问题。
4. **不要做的事**：把口径文档整篇当训练语料塞进去（等于让模型背文档，两篇实证都指向不划算）；把具体数字训进去。
5. **门槛**：攒到 **1000+ 条经过人工判定的高质量轨迹**再开训，否则样本里混一条错答案就是教坏一条。

## 8. 风险清单

| 风险 | 说明 | 对策 |
|---|---|---|
| 训练集混入错误答案 | 直接教模型犯错 | 入训前必须人工判定，宁少勿滥 |
| 过拟合到具体问法 | 换个说法又崩（就是上一版打地鼠的翻版） | 评测集留没见过的问法；强调变体覆盖 |
| 灾难性遗忘 | 通用能力退化 | LoRA 比全参轻，仍要抽检通用能力 |
| 知识过期 | 口径一改，权重里那份就成了"自信的错" | 口径永远只从文档/知识库走，不进权重 |
| 不可审计 | 权重里的知识查不到出处 | 保留 trace + 口径标注，回答仍要能追到表和公式 |

## 9. 一句话总结

**能训的是"怎么做事"，不能训的是"事实是什么"。**
所以微调不会让系统"不查知识库"，它会让系统**更老实地查、更准确地答、更少地编** —— 这才是它真正值钱的地方。
