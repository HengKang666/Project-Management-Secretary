# 判据规则（所有技能共用）

> 判断标准的唯一出处。业务方定了正式口径就改这里，所有技能同时生效。

## 一、前置：所有统计统一执行（每个技能都要过一遍）

| # | 规则 | 来源 |
|---|---|---|
| 1 | **按年度过滤**：只看当年度创建的项目。**只适用于「预算执行」「进度异常」「实时监控」三处**；**审批积压类技能（待我审批 / 流程监控 / 审批积压扫描）不按创建年度过滤** —— 卡最久的往往就是往年创建的项目，滤掉正好把最该清的藏起来；但要在回答里写明「含往年创建」 | 实测：不过滤时「审核中」平均年龄 1422 天、超期项目平均 1221 天，历史遗留把当期信号完全淹没 |
| 2 | **状态顺序**：草稿 → 提交审核 → 审核中 → 审核通过待施工 → 施工中 → 施工完成待验收。**已驳回、已取消不计入在办** | 实测 |
| 3 | **编号一律翻中文**：状态、缺陷类型在库里存的都是编号，按业务字典翻成中文再写，**不许凭字面猜** | 实测：库里状态、类型均为编码 |
| 4 | **作废/删除的记录一律排除**。**清单里不许出现「已作废」「已取消」「已驳回」这些状态的工单** —— 出现了就是没过滤干净，回去重查。（删除标记和状态是两回事，两个都要滤） | 实测：曾把「已作废」的工单列进异常清单 |
| 5 | **先对名字**：按供电所筛选前先确认库里的写法（简称/全称/有没有空格），对不上就如实说明，不要硬凑 | 实测 |

## 二、层级与范围

| # | 规则 | 来源 |
|---|---|---|
| 1 | **预算的口径单位是「供电所 / 二级公司（县公司）/ 全市」，不是台区**。给了一个台区名，先归到所属供电所再按所统计 | 实测：拿台区对预算永远是「0 元、占比 0%」 |
| 2 | 按提问人**权限层级**作答（全市 → 县公司 → 供电所）；问题没写层级时，按权限内能下钻到的最小完整层级答并注明范围 | 起始约定 |
| 3 | 层级定不下来就在回答里写清「按 X 层级统计」，让对方能一眼纠偏 | 起始约定 |

## 三、预算执行

| # | 规则 | 来源 |
|---|---|---|
| 1 | **已审批** = 审核通过待施工 / 施工中 / 施工完成待验收。**不算**：草稿、提交审核、审核中、已驳回、已取消 | 实测 |
| 2 | **未审批** = 草稿 / 提交审核 / 审核中 / 驳回后已修改。**不含**已驳回、已取消 | 实测 |
| 3 | 分配金额、已审批金额、未审批数量，**三者必须同年度、同层级**才能放一起比 | 实测 |
| 4 | **强制自查：预算使用占比必须 ≤ 100%**。超了就是口径没对齐，**回去按年度重算**；**绝对不许用「含往年结转」解释掉** | 实测：曾算出 381.93% |
| 5 | 2026 年基准值：分配 **1880.00 万** / 已审批 **128.08 万** / 占比 **6.81%** | 实测 |
| 6 | **达标判据**：设 P = 当年已过时间比例（已过天数 ÷ 全年天数）。<br>已审批占比 **< P × 0.6** → 未达标；**P × 0.6 ≤ 占比 < P** → 进度偏慢，按当前速度难达标；**占比 ≥ P** → 正常或超前 | 起始约定（0.6 取自实测 9 月已过 75%、执行 6.81%） |
| 7 | 说「未达标」必须同时给出：**差多少、剩多少时间、按当前速度能不能完成**。**禁止只写一句「未达到任务标准」就收尾**；**也不要把内部的 0.6 系数换算成「45% 基准线」写给人看**，直接说「已过 75%、执行 6.81%、缺口 93.19 个百分点」 | 实测：历史上只给结论；暴露内部阈值让人看不懂 |
| 8 | **原因判定**（按未审批项目数量三选一）：未审批数 = 0 且分配 > 0 → **没有项目可审批**（源头储备不足）；未审批数 > 0 → **项目有，卡在审批**（**必须同时给「已批 X 个 / 未批 Y 个」两个数**，只给一个不算） | 实测 |
| 9 | **建议必须从原因推出来、一一对应**：无项目 → 补储备（列出从哪些对象找：高损台区、频繁跳闸线路、低电压台区）；卡审批 → 清积压（卡在哪个节点、多少个、先清金额大的）；批了未完工 → 推施工；正常 → 只写保持节奏 + 风险点 | 实测 |
| 10 | **禁止的废话**：「加强管理」「提高效率」「高度重视」；每条建议必须有**对象和量** | 实测 |
| 11 | 不越权：超出提问人权限的事不提（如无权限不提跨所调剂），确需上级决策写成「需上级明确 X」 | 起始约定 |

## 四、预算空间（可用余额）

| # | 规则 | 来源 |
|---|---|---|
| 1 | **可用余额 = 该所当年度分配预算 − 该所当年度已审批金额**，两边都按年度对齐 | 实测：不过滤年份会算出负几十上百万 |
| 2 | 自查：已审批金额不得 > 分配预算；超了按「预算执行」第 4 条重算 | 实测 |
| 3 | 申报金额 > 余额 → **先明说超了多少**，再给两条出路：拆分为余额以内的核心内容；申请追加/统筹 | 实测 |
| 4 | 分配金额查不到或为 0 → 写「本年度未查得分配金额」，**不许拿 0 当分母算占比** | 实测 |

## 五、审批条件（六条，逐条给「符合 / 不符合 + 依据」）

| # | 判据 | 不符合时怎么说 | 来源 |
|---|---|---|---|
| 1 | **有工单载体** —— 每笔预算都有对应的缺陷工单 | 指出缺哪张载体 | 起始约定 |
| 2 | **预算装得下** —— 该所当年度可用余额 ≥ 申报金额（按第四节的算法） | 说清超多少、给两条出路 | 实测 |
| 3 | **类型匹配** —— 缺陷类型与实际治理对象一致（按第六节的对应表） | 指出建议归哪一类、为什么 | 起始约定 |
| 4 | **明细完整** —— 工程费、物资费都填了，且**工程费 + 物资费 = 申报总额**。核对必须用**精确到元**的原值，**不许拿四舍五入后的万元相加**（6.72 万 + 22.28 万 = 29.00 万 ≠ 28.99 万，这是四舍五入不是不齐）；真差异的判据是**差额超过总额的 1%**（实测全库 1325/5313 对不上，最大差 24.55 万元） | 指出缺哪一项、差多少 | 起始约定 |
| 5 | **工期合理** —— 有计划开完工时间；跨年的要有说明 | 指出缺时间或跨年问题 | 起始约定 |
| 6 | **金额可比** —— 不显著高于同类项目（按第八节） | 给出同类分布（最低/中位/最高）和偏差 | 实测 |

**一律不许写「基本符合」。** 六条必须**逐条**给结论和依据。
**每条先给结论，且结论只有三种：符合 / 不符合 / 无法判定。结论必须和后面的依据一致** —— 依据里写了「未超余额」就不能标「不符合」，写了「差异对得上」就不能标「不符合」。拿不准就标「无法判定」，不要先写一个不符合再圆回来。
**「无法判定」要说清是数据没有，不是项目不合格**（例如工期字段全库 99% 是空的）。

## 六、缺陷类型的对应（按治理对象判）

库里存的是**编号**，正式字典 DEFECT_TYPE 的对应关系如下（实测）：

| 编号 | 中文 | 编号 | 中文 |
|---|---|---|---|
| 1 | 线缆类-导线 | 11 | 线缆类-其他 |
| 2 / 19 | 台区线损 | 12 | 10kV线损 |
| 3 | 设备老化 | 13 | 设备类-其他 |
| 4 | 线缆类-杆塔 | 14 | 设备类-开关类 |
| 5 | 其他 | 16 | 设备类-环网柜 |
| 6 | 线缆类-电缆 | 17 | 电缆分支箱 |
| 7 | 树障 | 18 | 表计故障 |
| 8 | 设备类-柱上变压器 | 20 | 对地距离不足 |
| 9 | 表计故障 | 10 | 对地距离不足 |

**按治理对象判该归哪一类**：线路/杆塔 → 线缆类；台区线损 → 台区线损；变压器/开关/环网柜/分支箱 → 设备类；电表/表箱 → 表计故障；树障 → 树障。
编号 **必须翻中文**（实测库里绝大多数存的是编号，只有零星几条存了中文）；拿不准就写明判断理由，**不要硬填**。
**「其他」（编号 5）等于没填类型**，判「类型匹配」时应视为「未明确」。

## 七、进度异常

| # | 异常 | 判据 | 来源 |
|---|---|---|---|
| 1 | **超期** | 已过计划完工日 **15 天**以上仍未完工；分档 **15–30 / 31–90 / 90 天以上**。**注意：全库 5266/5313（99%）没填计划工期，这条当前基本用不了** —— 没填就写「无法判定」，改用审批停留天数 | 实测 |
| 2 | **落后** | 已过计划工期一半，状态仍停在「审核通过待施工」之前。落后一档 = 停在审核中；落后两档 = 停在草稿或提交审核 | 起始约定 |
| 3 | **停滞** | 需要「状态最后变更时间」，距今 **30 天**以上。**本库没有这个字段**（只有 create_time 和 update_time）→ **停滞一律写「无法判定」，不许拿 update_time 当替身** | 实测：拿 update_time 算会得出一片 77 天（是同一次批量更新造成的假信号）；不锁死会让同一个问题两轮结论从 191 条跳到 0 条 |
| 4 | **钱花了没动** | 金额排本所**前 10 位**，且状态停在「审核通过待施工 / 施工中」**超过 90 天** | 起始约定 |
| 5 | **年内完不成** | 按当前进度估算所需天数 > 当年剩余天数 | 起始约定 |
| 6 | **计划完工日缺失** | **缺就写「无法判定」，不设占比阈值、也不当异常**，同时把缺失数量作为数据质量反馈报出 | 实测：5266/5313（**99%**）没填 |

## 八、审批停留（积压）

| # | 规则 | 来源 |
|---|---|---|
| 1 | **数据来源**：审批节点在表 t_work_order_audit_task（node_name 节点名、create_time 进入节点时间）。**只有 task_status = 0（待处理）才算待办**；1 处理中、2 已完成、3 已驳回都不算。**这个字段是有的，不许说「缺少进入节点时间字段」就跳过计算** | 实测：129 条待处理 vs 142 条已完成，混了就把「已完成」当积压 |
| 2 | **停留天数 = 系统当天 − 进入当前节点的日期**（上游就算给了「统计截止」，也算到系统当天；「统计截止」只用来写「截至 X 月」这句话）；查不到进入时间用创建时间兜底并注明是估算 | 实测 |
| 2.1 | **上游传来的「变更时间」就是进入本节点的时间，不是今天。** 「今天」一律用系统当前日期；**不许把变更时间当成统计截止日**，否则刚转来的积压件会被算成「停留不足 1 天」 | 实测：曾把 4 月 17 日进节点、已卡 157 天的件说成「停留不足 1 天」 |
| 2.2 | 没填进入时间、也查不到记录 → 写「无法判定停留天数」，**不要补 0** | 起始约定 |
| 3 | 分档：正常 **≤ 15 天** / 偏慢 **16–90 天** / **积压 > 90 天** | 起始约定（实测历史遗留均值 1422 天，均值不可用） |
| 4 | 排序：**先按停留最久，其次按金额大** | 起始约定 |
| 5 | 上游传来的那张单据：如果它进到的正是当前角色的节点，**必须单独点出来**；不在也要说一句「这一张当前不在本节点」 | 实测 |

## 九、金额合理性（离群）

| # | 规则 | 来源 |
|---|---|---|
| 1 | 申请金额**高于同类历史最高值**，或**高于同类中位数 2 倍** → 判**离群**，必须给出可比项目清单 | 实测 |
| 2 | 可比范围**一档一档来，不许跳档**：先 **同所 + 同缺陷类型 + 近两年**；样本不足 5 个再退到 **同公司**；再不足才退到 **全市**。**三档都要报数，样本不够才退档，并且要写明为什么退**。这一段固定这么写：「同所同类型近两年 N 个（不足 5 个）→ 同公司 M 个 → 本次按【X 档】比，样本 K 个」。**只写一个「全市」而不说前两档有几个，算没答**。跳档会改变结论（实测同一张单子换档后从「离群」变「合理」），所以用哪一档必须让人看得见 | 实测：换档会换结论（同所最高 16.39 万 vs 全市最高 2.99 万） |
| 3 | 可比样本**少于 5 个**要明说「样本不足，仅供参考」，**不许下「显著偏高/偏低」这种结论**。可以陈述事实「高于已查得的 N 个同类项目的最高值 X 万元」，但结论必须写成「需人工复核」，**不许既说偏高又说无法判定** | 起始约定 |
| 4 | **必须给分布**（最低 / 中位 / 最高），不许只给一个平均数；并给出本项目排在同类的前百分之多少 | 实测 |
| 5 | 说「偏高」必须写清**拿哪几个同类项目比的** | 实测 |
| 6 | 实测参照：线缆类-杆塔 平均 3.43 万、最高 32.52 万 | 实测 |

## 十、数据质量

| # | 项 | 判据 | 来源 |
|---|---|---|---|
| 1 | 物资费占比 | **< 0% 或 > 100%** → 判数据异常 | 实测：出现过 224%（物资费 > 总额） |
| 2 | 明细合计 | 工程费 + 物资费 ≠ 申报总额 → 判明细不齐 | 起始约定 |
| 3 | 计划完工日缺失 | **只看数量，不设占比阈值** | 实测：缺失 99% |
| 4 | 指标原始值为空或 0 | 标「**该项暂无有效数据**」，**不是「问题最重」**，不能拿它当拿钱的理由 | 实测 |
| 5 | 上下级合计 | 公司级金额 = 各所合计，对不上说明版本没对齐，**要写明** | 起始约定 |

## 十一、实时监控阈值

| # | 指标 | 阈值 | 提醒对象 | 来源 |
|---|---|---|---|---|
| 1 | 预算执行率 | 低于 **已过时间 × 0.6** | 对应供电所 + 县公司财务 | 实测：9 月已过 75%、执行 6.81% |
| 2 | 审批停留 | 超过 **90 天** | 卡住的那个审批节点 | 起始约定 |
| 3 | 超期未完工 | 超计划完工日 **15 天以上** | 项目负责人 + 所属县公司 | 实测 |
| 4 | 物资费占比 | **< 0% 或 > 100%** | 数据维护方 | 实测 |
| 5 | 计划完工日缺失 | **只看数量** | 数据维护方 | 实测 |

- **越阈必须说三句**：越了多少、超了多久、该谁管。只说「超标了」不算。
- **没有阈值的指标不要报** —— 没有判据就没有异常。
- **连续两期恶化** = 同一指标最近两期都比各自的上期更差。
- **「今天最该关注的三件事」**：按「越阈幅度 × 涉及金额」排，**只给三件**。

## 十二、角色 → 可见范围（按角色类技能共用）

**角色的节点名就用审批任务表里的 node_name 真值**（实测存在的节点）：

| 角色（= node_name） | 可见范围 |
|---|---|
| 供电所内部审核 | 停在本节点的待处理任务 |
| 县公司运检部审核 | 停在本节点的待处理任务 |
| 营销部审核 | 停在本节点的待处理任务 |
| 县公司财务部审核 | 停在本节点的待处理任务 |
| 市公司财务部审核 | 停在本节点的待处理任务 |
| 市公司领导审批 | 停在本节点的待处理任务 |
| 申报人 | 自己提交后被打回、需修改重报的（驳回已修改） |
| 施工方 | 审核通过待施工 / 施工中 |
| 验收人 | 施工完成待验收的 |

**实测各节点待处理条数**（不是「审核中」全量）：供电所内部审核 92、营销部 18、县公司财务部 13、县公司运检部 5、市公司财务部 1。
**严禁把全库「审核中」的量当成某一个角色的待办。**

- **只给提问人这一个环节的**，**严禁**把「审核中」的全量丢给某一个角色。
- **申报人没有待审批清单**：以申报人身份问待审批，要回答「申报人没有待审批清单」。
- 「下一个环节该谁动」按前置里的状态顺序推。
- 来源：实测（曾把全量 1444 条给过单一角色）。

## 十三、年度计划类（16 指标 / 装填预算）

| # | 规则 | 来源 |
|---|---|---|
| 1 | 16 项指标分两类：**问题导向类**（线损、工单、停电时长、低电压）反映「问题重」；**基础信息与作业承载力类**反映「规模大」。**得分高 = 越需要资源，不是表现好** | 实测 |
| 2 | 治理目标**只从问题导向类 + 历史预算执行里挑**，定 **2~3 个**，每个写清：现状 → 按什么规则算分 → 提到什么水平能得多少分 → 对总分贡献 | 起始约定 |
| 3 | **排除「没有有效数据」的项**（见第十节第 4 条） | 实测 |
| 4 | 项目装填顺序：**目标匹配度 → 优先级 → 金额**；每排入一个写「已用多少 / 还剩多少」 | 起始约定 |
| 5 | 排入 / 剔除都要给清单，剔除要写理由；预算剩了或超了都要写明原因 | 起始约定 |
| 6 | 成效目标标「**建议值，需审定**」，参照同类最优或本所历史最好；没依据的写「暂无数据，暂不设定目标」，**不许编数** | 起始约定 |
| 7 | 成效必须与**申报时的预计值对照**（决算书/验收用），不能只报一个实际数 | 起始约定 |

## 十四、一致性自查清单（回答前逐条过一遍，不过不许交）

1. 占比 **≤ 100%**？
2. 分配 / 已审批 / 未审批是**同年同层级**？
3. 合计对得上（公司级 = 所级合计；工程费 + 物资费 = 总额）？
4. 判了离群，**给了可比项目清单**？样本 < 5 有没有说明？
5. 查不到的都写了「未查得 / 无法判定」，**没有估算、没有补 0**？
6. 编号都翻了中文？
7. 时间口径统一（超期 15 / 31 / 90；停留 ≤15 / 16–90 / >90）？
8. 上游传来的数据**直接采用**；与库里不一致时**以它为准并说明**？

## 十五、输出格式（所有技能共用）

| # | 规则 |
|---|---|
| 1 | **不要 Markdown 标记**：不写 `#` `##` `###`、不写 `**加粗**`、不画表格、不用代码块。分段用小标题就写纯文字，如「一、预算执行情况」 |
| 2 | 金额用**万元、两位小数**；比率**两位小数**；时长写「天」 |
| 3 | 不写数据库表名 / 字段名 / 英文标识 / SQL / 查询条件 / 返回行数 |
| 4 | 不写「数据来源」「溯源」「口径声明」「字段」「表」这类技术说明段 |
| 5 | 不提 AI、不提工具、不提查询过程、不写「本报告所有数字均可追溯」这类自我声明 |
| 6 | 期次编码换业务说法（202609 → 截至 2026 年 9 月） |
| 7 | 编号（缺陷类型、工单状态）一律翻中文 |
| 8 | 不要客套话、不要思考过程、不要「好的，我已经查到了足够的数据」 |
| 10 | **要「逐条」的地方必须一条一行列全**（13 条就 13 行），条数多就写得紧凑些。**这些段落里不许出现「等」「其余」「均在…以下」** —— 只要出现，就是没列全，回去补齐。字数限制不适用在清单上 |
| 10.1 | **清单的条数上限**：待列条目 **≤30 条就全列**；**超过 30 条**（例如全市 651 条异常）才允许只列前 20 条，但必须写明「共 N 条、其余 N−20 条合计 X 万元」。**「其余…条合计 X」这种写明剩余数的方式是允许的，用「等」字蒙过去不允许** |
| 11 | **库里的工单名很多是一整段描述，清单里要截短**：保留「对象名 + 治理动作」，控制在 25 字以内。**截的是名称，条目一条都不能少**（不许因为名字长就跳过某条） |

## 十六、硬规则（所有技能共用）

| # | 规则 |
|---|---|
| 1 | 每个数字都要有出处，**但出处不写进回答** |
| 2 | 查不到就写「未查得」或「无法判定」，**不许估算、不许补 0、不许拿别的年份顶** |
| 3 | **先结论、后依据**；技能文档规定的几段必须齐全，**不许缺段** |
| 4 | 上游传过来的数据**直接采用**；与库里不一致时**以它为准并说明** |
| 5 | **报数量前先数一遍**：说「N 个」就必须和你列出的条目数一致；对不上说明数字是估的，不是查出来的 |
| 6 | **合计一律用 SQL 的 SUM 求，不要在脑子里加**；报出去的合计必须等于逐条相加的结果（四舍五入允许差 0.01），对不上就别写合计 |
| 7 | **同一次回答里的同一个数只能有一个值**：开头概览、逐条清单、结尾建议里出现的同一个合计/条数，必须完全一致 |
