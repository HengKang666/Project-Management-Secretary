# 数据表说明书

> **这份文档是写「分析类 skill」的通用素材。** 任何「给一个供电所或供电公司出一份分析报告」的 skill，都先读这份。
> 各 skill 的差别只是**分析什么、回答哪些问题、输出什么格式**；表知识、口径、坑是共用的。
> 维护纪律：业务知识只写在**业务字典**（`ai_data.*`）与本文档里，代码里不写死 SQL、不另开表清单。

---

## 0. 动手前必须知道的四条纪律

1. **表只能查业务字典里登记的表**（`ai_data.ai_table_metadata`）。要加表 → 报维护方在字典里补行；不要另开一套表清单（那会变成第二套路由，必然和字典打架）。
2. **只读，且带 `deleted_flag = 0`**（有该字段的表）。不带就拿到历史版本 —— 实测评分明细表里旧版本有 7475 行、有效只有 737 行。
3. **一个事实只有一个出处。** 六项指标的**结果值**只在 `t_power_ai_metric_snapshot` / `_comparison`；明细推送表只作明细，不是结果值来源。
4. **编号必须翻成中文再进报告。** 库里存编号（如 `defect_type='8'`），中文在 `t_dict_data`。报告里直接抛编号等于没写。

## 1. 一条业务链要认的五个层次

```
组织：  公司(t_power_supply_company) → 供电所(t_power_company)
钱：    预算配置(公司级) → 预算分配结果(供电所级)
分：    评分标准(规则) → 评分明细(每所每项得分，含原始值/标准分/加权分/名次)
问题：  缺陷工单(项目) → 缺陷类型码表(编号→中文)
成效：  六项指标快照(结果值) + 同比环比
```

出一份分析报告，本质上就是在**这五层之间来回对账**：钱怎么分的 → 分对应哪几项得分 → 哪几项是真短板 → 库里的项目能不能治它 → 治完成效会变成什么。

## 2. 逐表说明

### 2.1 组织

| 表 | 做什么 | 粒度 | 关键字段 | 坑 |
|---|---|---|---|---|
| `t_power_supply_company` | 县级供电公司 | 一行一公司 | `id`、名称 | — |
| `t_power_company` | 供电所档案 | 一行一所 | `id`、所名、所属公司 | 公司 ID 不能当供电所 ID 用 |

### 2.2 钱

| 表 | 做什么 | 粒度 | 关键字段 | 坑 |
|---|---|---|---|---|
| `t_power_company_budget_allocation` | 公司级年度总预算（分配计算的输入） | 一行一公司一年一版本 | `county_company_id`、`year`、`total_budget`、`is_new`、`version` | **必须 `is_new=1`**；表里有 19 个历史版本，还夹着 `total_budget=280.00` 的脏行。实测 2026 年 `is_new=1` 共 4 条、合计 1880 万 |
| `t_power_company_budget_result` | **供电所级分配结果**（分配系统的最终产出） | 一行一所一年 | `power_station_id`、`power_station_name`、`total_score`、`k_value`、`adjusted_score`、`budget_amount`、`year` | 一个所在一年只有 1 行（实测 47 所全是 1 行）；滤 `deleted_flag=0` 后 47 行合计正好 1880 万，与配置表自洽。`budget_ratio` 不是百分比，别直接展示 |

### 2.3 分

| 表 | 做什么 | 粒度 | 关键字段 | 坑 |
|---|---|---|---|---|
| `t_power_company_scoring_standard` | **评分规则**：16 项指标的方向、满分基准、及格线、规则原文 | 一行一指标 | `metric_key`、`metric_name`、`direction`（positive/negative）、`full_score_pct`、`pass_score_pct`、`remark`（规则原文在这里） | `is_new=1` 才是当前的 16 行；`remark` 里写着「分类：基础信息/作业承载力/问题导向/历史预算执行」和文档权重，**引用规则要照抄它，不要自己编公式** |
| `t_power_company_rank_weight` | 各项权重与方向 | 一行一指标 | `metric_key`、`weight`、`direction`、`rank_type` | 23 行；`rank_type` 区分对象 |
| `t_power_station_score_detail` | **评分明细**：每所每项的原始值、标准分、加权分、名次 | 一行一所一指标 | `power_station_id/name`、`county_company_name`、`metric_key`、`raw_value`、`normalized_score`、`weighted_score`、`rank_no`、`year` | **只滤 `deleted_flag=0`**；实测只有 2026 年（47 所 737 行，16×47=752，有 15 个格子缺 —— 缺就标「数据缺失」，不许补 0）；`budget_execution_amount` 这一项 47 所里 40 所 `raw_value=0`，却因排名计分拿到满分 100，是假象，别用它推「资金缺口最大」 |

**得分的语义（最容易理解反的地方）**：`normalized_score` 衡量的是「这个所在这项上有多需要资源」。基础信息/作业承载力类分高 = 规模大；问题导向类分高 = 问题重。所以**找短板要找问题导向项里分高的那些**，不是分低的。

### 2.4 问题（项目）

| 表 | 做什么 | 粒度 | 关键字段 | 坑 |
|---|---|---|---|---|
| `t_power_work_order` | 缺陷治理工单（项目储备） | 一行一工单 | `power_company_name`、`power_area_name`、`power_line_name`、`defect_type`、`specialty`、`work_status`、`budget_total`、`plan_start_time`/`plan_end_time`、`actual_end_time`、`create_time`、`deleted_flag` | **`power_company_name` 字段名骗人，实际存的是供电所名**（实测「环潭供电所」）；表里**没有 `power_station_id`**，按所筛选只能用名字；`defect_type` 存的可能是编号也可能是中文（数据不规范），翻译时两种都要容错；`line_loss`/`outage_time`/`economic_benefit` 三列**几乎全空**（5313 行里只有 3~4 行），**不能靠它们判断项目治什么** |
| `t_dict` + `t_dict_data` | **系统码表**：编号 → 中文 | `t_dict` 一行一字典；`t_dict_data` 一行一码值 | `t_dict.dict_code`（`DEFECT_TYPE`/`WORK_STATUS`/`WORK_SPECIALTY`/`PROJECT_TYPE`）、`t_dict_data.data_value`、`data_label` | 用 `dict_code` 定位字典，**不要写死 `dict_id`**；同一编号在不同字典里含义不同，必须先过滤字典再匹配。实测 `defect_type=8` →「设备类-柱上变压器」 |
| `t_work_order_audit_task` | 工单审批任务（含驳回原因） | 一行一审批任务 | 工单 ID、节点、意见、结果 | 没有 `deleted_flag`；记录的是**任务条数**，不等于去重后的工单数 |

**项目「治什么」怎么判断**（库里没有这个现成字段，只能分析）：① `defect_type` 的中文（台区线损 / 10kV线损 → 治线损；设备类-柱上变压器 → 治低电压与可靠性；线缆类-* → 治线路老化）；② `work_name` / `scheme_description` 的文本（实测能读出「更换变压器」「清理树障」「低压电缆老化」这类内容）。**两者都要引用，并在报告里注明这是按缺陷类型与工单描述判读的**。

### 2.5 成效（六项指标）

| 表 | 做什么 | 粒度 | 关键字段 | 坑 |
|---|---|---|---|---|
| `t_power_ai_metric_snapshot` | **六项指标结果值**（售电量/线损率/意见工单/故障报修/平均停电时长/跳闸次数） | 一行一对象一期一指标 | `scope_type`(city/district/station)、`scope_key`、`scope_name`、`period_type`(year/yearToDate/month)、`period_key`、`metric_code`、`metric_value`、`better_direction`、`source_summary_type` | **本表没有 `power_station_id`，只能用 `scope_name` 筛**；同一个 `period_key` 可能有两组值，差别在 `source_summary_type`（`currentMonth`/`upCurrentMonth`）—— 不钉住它能读出差 8 倍的两个数；**供电所粒度用 `period_type='yearToDate'`**（实测 47 所）；`period_key` 年度值形如 `2024`/`2025`，月度形如 `202609` |
| `t_power_ai_metric_comparison` | 同比/环比结果 | 一行一对象一期一指标 | `scope_name`、`period_type`、`current_period_key`、`comparison_type`、`current_value`、`base_value`、`change_rate`、`trend_result` | 实测 `base_value` / `change_rate` **大量为空**（无基期），用之前先查非空率，别把空当 0 |
| `t_power_push_station_score` | 供电所**整改优先级**与低压问题指标 | 一行一所一月 | `obj_name`、`priority_score`(0~100，越大越该先整改)、`priority_month`、`D198`/`D168`(低电压天数)、`U_low`/`U_total`(低电压用户数/总用户数)、`C_outage`(停电次数)、`SAIDI_1`(户均停电时长) | 用 `priority_score` 排优先级，比只看得分更贴「先治谁」 |
| `t_power_push_*`（5 张明细） | 工单/停电/跳闸/售电/线损明细 | 明细行 | — | **只作明细**；`t_power_push_line_loss` 实测 **0 行**，线损要走快照表 |

## 3. 速查：要回答什么 → 查哪里

| 要回答 | 主表 | 必须一起做的过滤/关联 |
|---|---|---|
| 这个所这次分到多少钱 / 往年多少 | `t_power_company_budget_result`（本所） | `deleted_flag=0`；公司级总额走 `budget_allocation` 的 `is_new=1` |
| 钱为什么多了/少了 | 分配结果 + 评分明细 | 两期逐项对比；注意往年**评分明细可能没有**（实测只有 2026），那就只能用成效与排名对照 |
| 哪几项是真短板 | `t_power_station_score_detail` | 只看问题导向 + 历史预算执行那几项；滤 `deleted_flag=0`；排除 `raw_value=0` 的项 |
| 库里还有哪些项目、多少钱 | `t_power_work_order` | 按 `power_company_name`（实际是所名）筛；`deleted_flag=0`；金额用 `budget_total` |
| 这个项目是治什么的 | `t_dict*` + 工单文本 | 用 `dict_code='DEFECT_TYPE'` 翻译编号；中文与编号两种都要容错 |
| 现状成效是多少 | `t_power_ai_metric_snapshot` | `scope_type='station'` + `period_type='yearToDate'` + 最新 `period_key`；按 `scope_name` 筛 |
| 同比怎么样 | `t_power_ai_metric_comparison` | 先看 `change_rate` 非空率 |
| 先治哪个所 | `t_power_push_station_score` | `priority_score` 降序 |

## 4. 写一个新 skill 的套路（复用这份文档）

1. 先问清楚：**谁在使用、输入是什么、要产出什么格式**（例：供电所收到分配通知 → 出一份可上报的分析报告）。
2. 把这五层里**用得上的表**挑出来，套用第 3 节的速查。
3. 在 skill 文档里写清**每一步要回答什么、查哪些数据、怎么判断**，只写方法和口径，**不写死 SQL**。
4. 库里缺的字段/表 → 记成缺口，报维护方在字典里补（本文档不代替字典）。
5. 跑一遍真实数据校对：每个数字都能追到表和行数，追不到的删掉。
